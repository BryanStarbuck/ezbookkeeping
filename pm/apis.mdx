## Introduction

### Why this repo exists

This is a fork of [mayswind/ezbookkeeping](https://github.com/mayswind/ezbookkeeping) kept at
`github.com/BryanStarbuck/ezbookkeeping` for one purpose: to run **this operator's own money** on
their own machine, with their own years of bank statements in it, driven from wherever they happen
to be working. Upstream ezBookkeeping is a good self-hosted personal-finance web app — a Go server
with a Vue 3 front end in desktop and mobile editions, a SQLite (or MySQL/Postgres) database, a
wide importer shelf, multi-currency accounts and a statistics page. It is a web app, though, and the
operator does not live in a browser. They live in a terminal and in Claude Code.

So this fork grows two extra front doors — a CLI (`ezbk`) and a stdio MCP server
(`ezbookkeeping`) — and both of them need the same thing: **a way to ask the running app a
question, and a way to tell it to do something, that is not a browser and is not a human login.**

That is this spec.

This fork is the second of its kind on this machine. `~/BGit/Bryan_git/actual_budget_bryan/`
did the same thing to Actual Budget first, and its `pm/apis.mdx` is the model this spec was grown
from. Where the two apps are alike, the design is deliberately the same so a lesson learned in one
is a lesson learned in both. Where they differ — and they differ a lot: ezBookkeeping is a
multi-user, multi-currency **bookkeeping** app with no envelope budget, no rules engine and no undo
stack — this spec says so and designs for the app in front of it rather than the one it learned
from.

### Where this spec fits under that umbrella

Three specs, one stack:

```
                        ┌───────────────────────────────┐
   web browser ────────▶│  /api/v1   (upstream, JWT)    │──┐
                        └───────────────────────────────┘  │
                        ┌───────────────────────────────┐  ├─▶ pkg/services ──▶ the books
   `ezbk`  (cli.mdx) ──▶│  /machine/v1   apis.mdx       │──┘      (one set of
   MCP     (mcp.mdx) ──▶│  ← THIS SPEC   (API secret key)│         Go services)
                        └───────────────────────────────┘
```

[cli.mdx](./cli.mdx) says what the terminal surface looks like. [mcp.mdx](./mcp.mdx) says what the
agent surface looks like. **This spec says what is behind both of them**, and it is written first
among equals: a verb `ezbk` cannot serve and a tool the MCP cannot serve are both the same bug — a
missing route here.

### What the operator gets from it

Concretely, on a Tuesday evening:

- _"How much did I actually spend on groceries this year, by month?"_ — one route, the server's own
  aggregation, no model arithmetic anywhere in the chain.
- _"Create the 27 accounts in my statement archive and import all 12,007 transactions."_ — a
  manifest route, a provisioning route, and ezBookkeeping's own OFX/CSV converters parsing every
  file.
- _"Everything from ACME HARDWARE this year is Home Repair, not Shopping."_ — one bulk route, with a
  dry run that names the exact 46 transactions before anything moves.
- _"Northbank says $4,211.08 as of the 31st. What do I say?"_ — a reconcile route that returns the
  difference and, only if asked again, writes one visible adjustment.
- _"What's my net worth in dollars, counting the euro account?"_ — one route that converts with the
  app's own exchange rates and **names the rate and its date** in the answer.
- _"Undo that."_ — a route, because an agent that can write must be an agent that can be un-written,
  and ezBookkeeping has no undo stack of its own (§9.6).

### How it works — the idea

**One set of services, three faces.** The `ezbookkeeping` Go binary is the only long-running
process. The plane mounts inside its gin router and calls the **same** `pkg/services` functions the
browser's `/api/v1` handlers call. Every balance the browser shows, every number `ezbk` prints and
every figure the MCP hands a model comes out of those services. There is no second implementation
of anything to drift.

**The filesystem is the authentication.** The app mints a 256-bit random key into a `0600` file in
the operator's home directory. A caller that can read that file is already a process running as the
operator on the operator's machine — at which point it could open the SQLite file directly. The key
is not trying to stop that person. It is stopping _everything else_: the other user on the box, the
web page the operator happens to have open, the container on the same host, the phone on the Wi-Fi.

**Nothing computes twice.** The clients are thin on purpose (cli.mdx §5.4, mcp.mdx §9.4). If a
question needs arithmetic, the arithmetic happens here, once, in Go — and that is why this spec has
an analytics plane (§12) that **moves** the grouping and currency conversion upstream does in the
browser (`src/stores/statistics.ts`) into the server.

### How it works — the machinery

An `ezbk` or MCP call is:

1. HTTP to `127.0.0.1:8080/machine/v1/...` with an `X-Ezbk-Api-Key` header.
2. Five gates in order — loopback socket, origin + host, key, tier, input schema (§5.7, §19).
3. A handler that validates its arguments, resolves the **bound user** (§6), calls **one** service
   operation, and returns.
4. One JSON envelope, success or failure, always the same shape (§7).

Writes add a sixth step in front: the caller must first call the matching dry run or `plan` route,
read the `confirm_token` it returns, and echo it back (§9).

### What this spec covers

What upstream already offers and why it is not enough; the key; the bound user; the envelope; the
tier model; the write protocol and the undo journal; the complete route catalogue family by family;
a coverage matrix against the web UI; the analytics plane and the charting it feeds; the currency
rule; the ingest plane and manifest-driven account provisioning; the passthrough; the money, time and
identifier rules; limits, concurrency, security, open-source safety, testing, use cases, acceptance
criteria and build phases.

It does not cover argument parsing or terminal rendering (cli.mdx §7, §13), tool descriptions or
model-facing prompt design (mcp.mdx §9 and
[ai/mcp_prompt_ezbookkeeping.md](../ai/mcp_prompt_ezbookkeeping.md)).

## Goal

> **Everything a person can do in the ezBookkeeping web UI, a program can do over this plane — with
> the same Go services computing it, the same converters parsing every statement, one currency per
> number, and two switches plus a token standing between an agent and the operator's real money.**

Five halves to that sentence, and each is a rule the build is measured against:

| Half                             | The rule                                                                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Everything the UI can do**     | §11's coverage matrix has a row per UI action and a route per row. A blank cell is a backlog item, never a shrug.                      |
| **The same services**            | No route reimplements a calculation the server already does. Where upstream computes in Vue, the calculation **moves** here (§12).     |
| **The same converters**          | A statement file is parsed by `pkg/converters`, the code the UI's Import dialog uses — never by a parser we wrote beside it (§14.4).   |
| **One currency per number**      | Every amount carries its currency; nothing is summed across currencies without a rate the response names (§13).                        |
| **Two switches and a token**     | Server tier, client switch, `dry_run: false`, and a `confirm_token` the caller can only have read from a plan (§9).                    |

## 2. What already exists upstream, and why we do not simply use it

This section exists because the obvious objection is _"ezBookkeeping already has API tokens and an
MCP server — why build a third door?"_ It does, and both are good. Neither is the thing this fork
needs, and the reasons are specific.

### 2.1 What upstream ships today

| Upstream feature           | Where                                                                             | What it is                                                                                                                                                             |
| -------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`/api/v1/*`**            | `cmd/webserver.go` `startWebServer()` lines 336–512                               | ~100 GET/POST `.json` routes the Vue app calls. Envelope `{success, result}` / `{success:false, errorCode, errorMessage}`                                              |
| **API tokens**             | `pkg/services/tokens.go` `CreateAPIToken()` · `pkg/api/tokens.go` `TokenGenerateAPIHandler()` | A JWT of token type 8 (`API`), per user, signed with a random 10-char secret stored in `token_record`. Full access to every `/api/v1` route. **Off by default** (`[security] enable_api_token = false`) |
| **The MCP server**         | `POST /mcp` · `pkg/mcp/` · `pkg/api/model_context_protocols.go`                    | JSON-RPC over HTTP, MCP token type 5, **seven tools** (`add_transaction`, `query_transactions`, `query_all_accounts`, `query_all_accounts_balance`, `query_all_transaction_categories`, `query_all_transaction_tags`, `query_latest_exchange_rates`). **Off by default** (`[mcp] enable_mcp = false`) |
| **CLI token minting**      | `cmd/user_data.go` — `userdata user-session-new --type api\|mcp`                   | Mints either token straight into the database, no password                                                                                                              |
| **`ebktools.sh` / `.ps1`** | `skills/ezbookkeeping/scripts/`                                                    | A curl + jq client for 13 `/api/v1` commands, reading `EBKTOOL_TOKEN` from the environment or a `.env` file                                                              |

### 2.2 Why none of them is the machine plane (LOCKED)

1. **An upstream token is a human's credential with no scope.** An API token opens **every**
   `/api/v1` route for its user — including `data/clear/all.json`, which erases the books, and
   `tokens/generate/*`. There is no read-only token, no write tier, no dry run and no ceiling. An
   agent holding one can do anything the operator can, in one call, with nothing in between.
2. **Getting one takes a password, a click or a database write.** The web route requires the
   operator's password; the CLI route writes the database directly. Neither is "the app mints its
   own key and the CLI simply finds it" — the requirement this fork was asked to meet.
3. **It travels.** A bearer JWT in an `Authorization` header is designed to be sent from anywhere
   `api_token_allowed_remote_ips` permits. The machine plane is designed to be **unreachable** from
   anywhere but this computer (R10).
4. **The upstream MCP is small by design and money-unsafe for our rules.** Seven tools, no
   statistics, no updates, no import, and amounts on the wire as **decimal strings** (`"12.34"`),
   which our integer rule (§17.1) forbids.
5. **Every one of them lives in upstream's files.** Growing them means editing `pkg/api/*.go`,
   `pkg/mcp/*.go` and `cmd/webserver.go` in hundreds of places — merge conflicts forever. The
   machine plane is one new package and a two-line mount (§4.1).

**What we do with them (LOCKED).** Nothing. They stay upstream's, they stay **off** in this fork's
`just run` (the recipe never sets `EBK_SECURITY_ENABLE_API_TOKEN` or `EBK_MCP_ENABLE_MCP`), and the
machine plane neither reads nor mints an upstream token. `ezbk doctor` reports if either has been
switched on, because an operator who enabled them for an experiment and forgot has a full-access
bearer door open that none of this spec's gates guard.

### 2.3 What we DO reuse (LOCKED)

- **`pkg/services`** — every read and write goes through the same service functions the `/api/v1`
  handlers call: `services.Accounts`, `services.Transactions`, `services.TransactionCategories`,
  `services.TransactionTags`, `services.TransactionTagGroups`, `services.TransactionTemplates`,
  `services.ExchangeRates` (via `pkg/exchangerates`), `services.InsightsExplorers`.
- **`pkg/converters`** — every statement file is parsed by
  `converters.GetTransactionDataImporter(fileType)` (`pkg/converters/transaction_data_converters.go`
  line 37), the same registry the Import dialog uses.
- **`pkg/models`** — request and response shapes. The plane returns upstream's model fields in
  upstream's casing (camelCase) wherever a model exists (§7.1a).
- **`pkg/errs`** — upstream errors are mapped, not re-invented (§7.2).

## 3. The eleven design rules

Each of these has shown up as a real bug in a real finance tool. They are stated once, here, and
every route in §10 is written to obey them. R1–R10 are Actual Budget's rules carried over; **R11 is
this app's own.**

**R1 — One service call per route.** A route validates, calls one service operation, and renders.
The exception is explicitly-named **composed routes** (reconcile, analytics, ingest apply, batch,
undo), which say so in their entry and carry `meta.composed: true`.

**R2 — Money is an integer number of hundredths.** Every amount in every argument, every response
field and every intermediate value. Never a float, never a decimal string, never "dollars just for
this one". §17.1.

**R3 — Absent is not zero.** A category with no transactions in a period is **absent** from a
breakdown, not present with `0`; an average over a period with no data is `null`; a balance we could
not compute is an error, not `0`. §17.3.

**R4 — Every write has a dry run.** `dry_run` defaults to **true** on every write route where a
preview is meaningful. The preview is produced by the same code path as the write (§9.2).

**R5 — Every cap is reported.** A clamped result carries `meta.truncated: true` and
`meta.limitApplied`. A silent cap is how a caller concludes an account has exactly 1,000
transactions. §7.5.

**R6 — Every error names a fix.** `error.hint` is a remediation the caller can act on, in the
caller's vocabulary. §7.4.

**R7 — The app decides, we report.** Where the app has an opinion — what a balance is, what a
converter parsed a row as, what an exchange rate is — the route returns the app's verdict verbatim.

**R8 — Reads never mutate.** No read-tier route writes to the books, the filesystem or the token
table. `POST /ingest/extract` is the one read-tier route that writes, only to the staging directory,
and says so in its entry.

**R9 — Fail closed.** No key, no plane. No bound user, no data. No tier, no route. No schema match,
no handler. A 404 is the answer to everything the caller was not supposed to reach.

**R10 — The plane is loopback-only, forever.** There is no configuration that binds it to another
interface and no flag that turns the origin gate off — including when the server itself is started
with `http_addr = 0.0.0.0`. Remote access to ezBookkeeping is what `/api/v1` and its JWTs are for.

**R11 — One number, one currency.** Every amount on the wire travels with its ISO 4217 code. Two
amounts in different currencies are never added, compared or ranked against each other unless the
route converted them with the app's rates and **names each rate and its timestamp** in the
response. §13.

```
├── ai/mcp_prompt_ezbookkeeping.md the MCP's instructions payload
└── pm/                            product management. NO CODE, EVER
```

**Why `pkg/machine/` and not beside `pkg/api/`.** The whole delta to upstream's tree is meant to be
**one `machine.Mount(router, config)` line** in `cmd/webserver.go` (after the `/api/v1` group, before
the listener) and **one `machine.Arm()` call** reached from server startup — a merge-conflict surface
of two lines rather than two hundred. A package upstream has never heard of cannot conflict with an
upstream commit; a file inside `pkg/api/` eventually will.

**Why not a second process.** A second binary is a second thing to start, a second port to pin, a
second health endpoint to get wrong, and a second writer on `data/ezbookkeeping.db` — SQLite with two
writers is a `database is locked` at 2 a.m. One process, one writer.

**The one table we add.** The ingest plane needs a durable record of which statement row became which
transaction (§14.6), and the undo journal needs somewhere to live (§9.6). Both are tables owned by
`pkg/machine`, created with `xorm` `Sync` inside `Arm()` in the **user-data** database — never by
editing `cmd/database.go`'s upstream table list. Their names are prefixed `machine_` so nobody
mistakes them for upstream's, and dropping them loses no upstream data.

### 4.2 Build integration

`just build` already builds the Go binary and the Vue front end. The plane is part of the Go binary
and needs no separate step. `just build` additionally builds `cli/` and `mcp/` (cli.mdx §2.3,
mcp.mdx §4). `just run` arms the plane; the boot line
`Machine plane armed on /machine/v1 (key 4f2a…/sha256:9c1b, user "operator", writes DISABLED)` is the
operator's proof it is up.

Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/mount.go` — function `Mount()`

## 5. Authentication — the API secret key

This section is the **authority**. cli.mdx §4 and mcp.mdx §6 restate parts of it for their own
readers; where they differ, this text is correct.

### 5.1 Why not a password or an upstream token (LOCKED)

1. **A password is typed by a human.** A CLI that prompts cannot run in a loop; an MCP that prompts
   hangs a conversation.
2. **An upstream API token unlocks everything** (§2.2) and is designed to travel.
3. **Both are the operator's.** The API secret key authenticates _this machine_, not a person, and
   never leaves it, so its blast radius is this computer.

### 5.2 Shape and entropy (LOCKED)

> **32 bytes from Go's `crypto/rand`, rendered as 64 lowercase hex characters.**

- **At least the length of a UUID, on purpose longer.** The requirement is "a very large key, the
  length of a UUID, from a cryptographically secure generator". A UUIDv4 is 36 characters carrying
  122 random bits. This key is 64 characters carrying **256** random bits — more than twice the
  entropy, and it is deliberately _not_ UUID-shaped: a UUID looks like an identifier, and
  identifiers get logged, put in URLs and pasted into issues. A 64-character hex string looks like a
  secret and gets treated like one.
- **`crypto/rand.Read` and nothing else.** `math/rand` is a seeded PRNG and is not cryptographically
  secure. A test asserts `pkg/machine` imports `crypto/rand` for minting and that `math/rand` appears
  nowhere under `pkg/machine/` or `cli/` (and `Math.random` nowhere under the TypeScript `mcp/`, which
  mints with `crypto.randomBytes`). A short read from `crypto/rand` is a fatal error,
  never a retry with a weaker source.
- **Not `security gen-secret-key`.** Upstream's `ezbookkeeping security gen-secret-key` makes a
  random _alphanumeric_ string for `[security] secret_key`. That is a different secret with a
  different job (below), and reusing the generator would blur the two.
- **Validated on every read.** `^[0-9a-f]{64}$`. A key that does not match is refused at resolve
  time with the rotate command as the hint — never silently padded, trimmed or lowercased.

**It is NOT `data/.secret_key`.** The fork's `justfile` writes `data/.secret_key` with
`openssl rand -hex 24` and passes it as `EBKCFP_SECURITY_SECRET_KEY`. That is upstream's
`[security] secret_key`, which encrypts 2FA secrets and salts passcode hashes
(`pkg/services/twofactor_authorizations.go`). It lives inside the repo directory (git-ignored by
`/data/`), and it must stay unrelated to the API secret key: rotating one must never invalidate the
other, and the API secret key must never live inside the repo tree at all.

Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/credentials.go` — `MintKey()`, `IsWellFormedKey()`, `Fingerprint()`

### 5.3 Where it lives (LOCKED)

```jsonc
// ~/.credentials/ezbookkeeping.json          mode 0600, directory mode 0700
{
  "ezbookkeeping": {
    "machine": {
      "api_key": "4f2a…64 hex chars…",
      "created": "2026-09-21T10:04:11Z",
      "created_by": "server",          // or "ezbk" or "mcp" — whoever needed it first
      "label": "operator-macstudio",
      "username": "operator"           // optional — the bound user (§6)
    },
    "statements": { "root": "/…/bank_statements" },
    "timezone": "America/Los_Angeles"  // optional — §17.4
  }
  // …other products' top-level keys, preserved byte for byte

```

- **One file unique to this application**: `ezbookkeeping.json`, beside `actual_budget.json`,
  `large_files_bridge.json` and the rest. Never shared with the Actual Budget fork — two apps, two
  keys, so a key leaked from one opens nothing in the other.
- **`~/.credentials/`, not the repo.** The repo is public (§20). There is no config key anywhere in
  the tree that can hold this value.
- **Per machine, never synced.** A second machine mints its own.
- **The write merges.** Read, mutate the `ezbookkeeping` subtree, write back — every key it does not
  own preserved.
- **The write is atomic and refuses symlinks.** Temp file in the same directory opened with
  `O_CREATE|O_EXCL` at mode `0600` from creation (never `chmod` afterwards), `fsync`, `rename`. If
  the destination is a symlink, the write is abandoned — that is somebody redirecting our secret.

### 5.4 Who mints it, and when (LOCKED)

**The web app mints it for itself, with no operator action at all.** `machine.Arm()` runs at server
boot, resolves the key, finds none, and mints one. By the time the operator first types `ezbk` or
first asks Claude Code a question, the key is there, and nobody had to be told about it. If it
already exists, the server uses the pre-existing key unchanged.

`ezbk` and the MCP may also mint — whichever of the three needs it first — under three rules:

1. **Mint at boot, never at import.** Resolving the key _creates_ one. Doing that in a package
   `init()` means every `go test` that imports the package writes a secret into the developer's real
   home directory. `Mount()` registers routes holding no key; `Arm()` arms them from server startup.
2. **The mint is a compare-and-set.** The writer re-reads inside the write and yields if a key
   appeared, then reads back and trusts the file rather than its own mint. Three processes starting
   at once converge on one key instead of three.
3. **Until it is armed, the plane 404s everything** (R9) — the same answer a stranger gets.

`ezbk key init` and `ezbk key rotate --yes` are conveniences over the same code path.

### 5.5 Resolution order (LOCKED)

First hit wins:

| #   | Source                                                          | For                                               |
| --- | --------------------------------------------------------------- | ------------------------------------------------- |
| 1   | `EZBK_API_KEY` / `EZBKMCP_API_KEY`                              | CI, one-off overrides. Never in a checked-in file |
| 2   | `EZBK_API_KEY_FILE` / `EZBKMCP_API_KEY_FILE`                    | the Docker-secret shape                           |
| 3   | `~/.credentials/ezbookkeeping.json`                             | **the normal path**                               |
| 4   | mint one (server always; `ezbk`/MCP only on first need)         | first run                                         |

`EZBK_CREDENTIALS_FILE` / `EZBKMCP_CREDENTIALS_FILE` relocate step 3 — the seam every test uses,
and why no test touches a real home directory. The server honours `EZBK_CREDENTIALS_FILE` too.

**Why not `EBK_*`.** Upstream reads every `EBK_<SECTION>_<KEY>` variable as a config override
(`pkg/settings/setting.go` `getConfigItemValueFromEnvironment()`). A variable named
`EBK_MACHINE_API_KEY` would look like a `[machine]` section to anyone reading that loader, and a
future upstream `[machine]` section would collide with it. Our prefix is `EZBK_` so the two
namespaces cannot meet.

### 5.6 How it is sent, and how it is checked (LOCKED)

```http
POST /machine/v1/transactions HTTP/1.1
Host: 127.0.0.1:8080
X-Ezbk-Api-Key: 4f2a…
X-Ezbk-Client: ezbk/0.1.0
Content-Type: application/json
```

- **A header, never a query parameter.** Query strings land in upstream's request log
  (`[server] log_request`), shell history and `Referer`.
- **`X-Ezbk-Api-Key`, not `Authorization: Bearer`.** Upstream's `JWTAuthorizationByHeader` already
  owns `Authorization` on this server; a second meaning for the same header is a middleware-ordering
  bug waiting. And proxies, browsers and HTTP libraries all have special handling for
  `Authorization`; a bespoke header gets none of that helpfulness.
- **Constant-time comparison, safe on unequal lengths.** Both sides are hashed with SHA-256 to a
  fixed width and compared with `crypto/subtle.ConstantTimeCompare`, so one comparison of
  equal-length buffers always runs and the length is never an oracle.
- **The 401 body is constant.** `{"ok":false,"error":{"code":"unauthorized"}}` — byte for byte the
  same for a missing key and a wrong one. The client does the explaining (cli.mdx §4.5 R6).
- **Upstream's request logger must not see the key.** `middlewares.RequestLog` logs paths, not
  headers, today. A test asserts no log line under `log/` ever contains the key pattern after a full
  suite run, so an upstream change that starts logging headers fails our build rather than leaking.

### 5.7 The gate ladder (LOCKED)

Order is load-bearing. Nothing below a gate runs until it passes.

| #   | Gate              | Refuses                                          | Answer                             |
| --- | ----------------- | ------------------------------------------------ | ---------------------------------- |
| 1   | Loopback socket   | another computer                                 | `404`                              |
| 2   | Origin + Host     | a web page on this computer; DNS rebinding       | `404`                              |
| 3   | The key           | another user on this computer                    | `401`, constant body               |
| 4   | Tier              | a write with the tier off; admin from the MCP    | `403 write_disabled` / `forbidden` |
| 5   | Input schema      | a malformed or unknown argument                  | `400 invalid_input`                |
| 6   | Confirm + ceiling | a write with no token, a stale token, or too big | `403` / `409`                      |

**Two facts about the server this mounts inside that gates 1 and 2 must survive:**

1. **`router.SetTrustedProxies(config.TrustedProxyTextualIPs)` is global** (`cmd/webserver.go`
   line 107), so gin's `c.ClientIP()` is derived from `X-Forwarded-For` / `X-Real-IP` whenever a
   proxy is trusted — attacker-controlled. Upstream's own IP limits (`APITokenIpLimit`,
   `MCPServerIpLimit`) use `ClientIP()`, which is right for them and wrong for us. **Gate 1 reads
   `c.Request.RemoteAddr` — the kernel's view of the peer — and never calls `c.ClientIP()`**, never
   reads `X-Forwarded-For` or `X-Real-IP`. Accepted peers: `127.0.0.1`, `::1`,
   `::ffff:127.0.0.1`. A remote request carrying `X-Forwarded-For: 127.0.0.1` gets a 404, and a test
   says so. A **Unix-socket** listener (`[server] protocol = socket`) is treated as loopback only if
   the socket file is `0600`-owned by the current uid; otherwise the plane refuses to arm.
2. **"Arrived on loopback" includes any web page the operator has open.** ezBookkeeping sets no CORS
   headers today, so a cross-origin page cannot _read_ a response — but it can still _send_ a
   simple request, and a DNS-rebound hostname turns a remote page into a same-origin one. The key is
   what stops it; gate 2 is the second wall. A browser always sends `Origin`, `Sec-Fetch-Site` or
   `Sec-Fetch-Mode` and cannot be talked out of them; `ezbk`, the MCP and `curl` send none, so
   **presence is the signal**. Any request with an `Origin` header, or a `Sec-Fetch-Site` or
   `Sec-Fetch-Mode` header other than absent, is `404`. The plane also pins `Host` to
   `127.0.0.1:<port>` / `localhost:<port>` / `[::1]:<port>` — rebinding is precisely the trick that
   has to lie about `Host` — and sets `Cache-Control: no-store` and `Vary: Origin` on every answer.

   **A consequence for clients written in Node:** Node's `fetch` is undici, which stamps
   `Sec-Fetch-Mode: cors` on every request and gives the caller no way to remove it, so a `fetch`
   client is a browser to this gate and gets `404` forever. The MCP therefore speaks `node:http` /
   `node:https` and carries a canary that fails on any `fetch(` in its source (mcp.mdx §8). Any future
   Node client of this plane has the same constraint.

**The plane is loopback-only even when the server is not.** Upstream's default is
`http_addr = 0.0.0.0`; the fork's `justfile` overrides it to `127.0.0.1`, but an operator can undo
that. Gate 1 does not care what the listener is bound to: a phone on the Wi-Fi reaching
`192.168.1.20:8080/machine/v1/ping` gets a 404 regardless. When the listener is non-loopback, the
boot line says so loudly, because the browser door (`/api/v1`) is then network-reachable even though
this one is not.

Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/gates.go` — `isLoopbackSocket(c)`, `isBrowserRequest(c)` (`Origin`, `Sec-Fetch-Site`, `Sec-Fetch-Mode`), `hostAllowed(c)`, `keyMatches(c)`

### 5.8 Rotation, and what the key is not

**Rotation** is `ezbk key rotate --yes`: mint, merge-write, print the new fingerprint. The running
server still holds the old key in memory, so the operator restarts it — until they do, every call
returns `401` with the client's hint `restart the server: ezbk stop && ezbk up`. A plane that
hot-reloads its own credential is a plane where a stolen key is revoked "eventually".

**The fingerprint** — `4f2a…/sha256:9c1b`, the first four hex characters plus a SHA-256 prefix — is
the **only** representation of the key that may be logged, printed, put in an error or shown to a
model.

**What the key is NOT:**

- Not a user identity. It authenticates _the machine_; the user is the bound user (§6).
- Not a capability grant. Holding it does not enable writes; the tier switches do (§8).
- Not an upstream token. `/api/v1` and `/mcp` never accept it, and `/machine/v1` never accepts a JWT.
- Not `[security] secret_key`. That encrypts 2FA secrets; this authenticates callers.
- Not an API key in the SaaS sense. It is never sent off this machine, by anything.

## 6. The bound user — whose books the key opens

This section has no counterpart in the Actual Budget spec, because Actual opens **a budget file**
and ezBookkeeping opens **a user's data**: every account, transaction and category row carries a
`uid`, and every upstream handler reads it from the JWT claims. The machine key carries no user. So
the plane binds to exactly one.

### 6.1 Resolution (LOCKED)

First hit wins:

| #   | Source                                                         |
| --- | -------------------------------------------------------------- |
| 1   | `EZBK_MACHINE_USERNAME` in the **server's** environment        |
| 2   | `ezbookkeeping.machine.username` in the credentials file       |
| 3   | the database has exactly **one** non-deleted user → that user  |
| 4   | **nothing**                                                    |

**No user is ever guessed.** With zero users the plane answers `not_ready` with the hint _"register
the first user at http://localhost:8080/ (the plane binds to it automatically)"_. With two or more
and nothing configured, every data route answers `not_ready` naming the usernames that exist and the
setting to choose one. Choosing a user's books on the operator's behalf is the worst mistake
available on this plane — it is Actual's "never guess a budget" rule (its apis.mdx §8.0) moved to
the thing that plays that role here.

### 6.2 How the binding reaches the services

The plane resolves the bound user's `uid` once at arm time and again whenever `whoami` is asked (a
deleted or renamed user is noticed, not cached forever), then calls services with that `uid` exactly
as an upstream handler does with `c.GetCurrentUid()`. It never constructs a JWT, never inserts a
`token_record`, and never appears in the user's session list — `ezbk` activity is not a "session",
and a phantom session in the Security Settings page would be the operator's first sign of an
intruder that is not one.

### 6.3 The bound user's restrictions still apply (LOCKED)

ezBookkeeping has per-user **feature restrictions** (`pkg/core/user_feature_restriction.go`, values
1–19 — e.g. restrictions on data import, data export, clearing data). The plane honours them: a
route whose upstream counterpart checks a restriction checks the same one, and refuses with
`forbidden` naming it. An administrator who restricted a user did not mean "except from the
terminal".

**2FA is deliberately not asked.** Two-factor protects a _human login_ reachable from a network. The
machine plane is not a login and is not network-reachable (R10); the key proves "running as this OS
user on this computer", which is a stronger statement than a TOTP code about where the caller is.
`whoami` reports whether the bound user has 2FA on, so nobody is surprised.

### 6.4 Every response names the user

`meta.user` (username) is on every data response, the way Actual's `meta.budgetName` is — the
cheapest defence against a caller that has drifted onto the wrong books.

Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/binduser.go` — `ResolveBoundUser()`, `BoundUid(c)`

## 7. The transport contract

### 7.1 The envelope (LOCKED)

Every response, success or failure, is one JSON object of the same shape.

```jsonc
// success
{
  "ok": true,
  "data": { /* route-specific */ },
  "meta": {
    "target": "local",
    "user": "operator",
    "defaultCurrency": "USD",
    "serverVersion": "2.0.1",
    "commit": "e136e51",
    "asOf": "2026-09-21T18:41:02Z",
    "timezone": "America/Los_Angeles",
    "tookMs": 38,
    "truncated": false,
    "tier": "read"
  }
}

// failure
{
  "ok": false,
  "error": {
    "code": "not_found",
    "message": "No account with that id.",
    "hint": "GET /machine/v1/accounts — or pass account_name instead of account_id",
    "details": { "id": "3401855937219633152" },   // optional, structured, never a stack
    "upstreamCode": 204001                         // optional — the pkg/errs code, when one caused it
  }
}
```

**This is not upstream's envelope, on purpose.** `/api/v1` answers `{success, result}` and
`{success:false, errorCode, errorMessage, path}`. The machine plane answers `{ok, data, meta}` and
`{ok:false, error:{code, message, hint}}` — the same shape the Actual Budget fork's plane uses, so a
human or a model that has learned one of this operator's finance planes has learned both. The
upstream code is kept in `error.upstreamCode` so nothing is lost in the mapping.

### 7.1a Casing (LOCKED)

- **`meta` and `error` are ours, and camelCase.**
- **`data` carries upstream's model fields in upstream's casing — camelCase** (`sourceAccountId`,
  `categoryId`, `utcOffset`) — wherever a `pkg/models` response type exists. Renaming them would be a
  translation layer that drifts.
- **Arguments are snake_case** (`account_id`, `start`, `category_ids`), matching the MCP's tool
  arguments and upstream's own query-string convention (`category_ids`, `max_time`).
- **Our additions to `data`** (analytics series, plans, provenance) are camelCase, like upstream's.
- **`data` is never a bare array.** A list route returns `{ "accounts": [...] }`.

### 7.2 The nine codes (LOCKED)

`unauthorized` · `forbidden` · `not_found` · `invalid_input` · `conflict` · `write_disabled` ·
`not_ready` · `upstream_error` · `internal`

| Code             | HTTP | Means                                                                                          |
| ---------------- | ---- | ---------------------------------------------------------------------------------------------- |
| `unauthorized`   | 401  | gate 3 — no key or wrong key                                                                   |
| `forbidden`      | 403  | gate 4 — admin route; a user feature restriction; the MCP asking for admin                     |
| `not_found`      | 404  | gates 1–2, an unknown route, or a real missing entity                                          |
| `invalid_input`  | 400  | gate 5 — schema, range, or an argument combination that cannot hold                            |
| `conflict`       | 409  | the world changed under the caller — stale token, duplicate submission, ambiguous name          |
| `write_disabled` | 403  | gate 4 — a write route with the tier off                                                       |
| `not_ready`      | 503  | the plane is not armed, no user can be bound, or the database is not open                      |
| `upstream_error` | 502  | a service returned an error we can name (mapped from `pkg/errs`); the hint points at `~/T/ezbookkeeping/error.err` |
| `internal`       | 500  | anything else; the message is generic and the detail is in `~/T/ezbookkeeping/error.err`      |

**Mapping from `pkg/errs` (LOCKED).** Upstream's codes are `category*100000 + subcategory*1000 +
index` (`pkg/errs/error.go`). The mapping is a table in `envelope.go`, not a guess per handler:
`*NotFound` errors → `not_found`; `ErrIncompleteOrIncorrectSubmission`, `ErrPageCountInvalid` and the
other validation errors → `invalid_input`; `ErrRepeatedRequest` → `conflict`; feature-restriction and
`ErrIPForbidden` → `forbidden`; `ErrOperationFailed` and database errors → `upstream_error` with the
upstream code attached; anything unmapped → `internal`, logged with its code so the table can grow.

**Where the detail goes.** Every fault the plane answers with `internal` or `upstream_error` is also
written, with its stack and its cause chain, to `~/T/ezbookkeeping/error.err` — the one error file all
three processes of this fork share ([error_err.mdx](./error_err.mdx)) — and both codes' hint says so:
_"read ~/T/ezbookkeeping/error.err for the server-side detail"_. An answer to the caller (a 4xx-shaped
code) is recorded as expected and never bloats that file. Neither hint ever carries the stack itself
(§19.3).

Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/envelope.go` — `Upstream()`, `toFail()`, `reportLost()`

**A tenth code is a spec change, not a commit.** mcp.mdx §12.3 lists twelve: the three extra
(`confirm_required`, `too_many_changes`, `wrong_server`) are minted by the MCP and never appear on
this wire. Every code here is also an MCP code; a test asserts the superset.

### 7.3 Versioning (LOCKED)

The path carries the version: `/machine/v1/`. Within `v1`, adding a route, an optional argument or a
response field is not breaking; removing or renaming anything, or changing a field's type or units,
is `v2`. `GET /capabilities` (§8.3) is how a client discovers what this build has.

**Upstream version drift is not our version.** ezBookkeeping moves (2.0.1 today); when an upstream
merge changes a model field the plane passes through, the plane's `v1` contract is what the clients
depend on, and `money.go` / the response projectors absorb the change. A test pins the shape of every
`data` object against a committed fixture, so an upstream field rename fails our build at merge time
rather than surfacing as a model reading `undefined`.

### 7.4 Errors name a fix (R6)

| Bad hint                 | Good hint                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------ |
| "Invalid account."       | `GET /machine/v1/accounts` — or pass `account_name` instead of `account_id`          |
| "Write disabled."        | Set `EZBK_MACHINE_ALLOW_WRITE=1` for the server and restart it (`ezbk stop && ezbk up`) |
| "Too many changes."      | 1,904 rows would change; raise `max_changes`, or narrow with `start`                 |
| "Not ready."             | Two users exist (`operator`, `guest`); set `ezbookkeeping.machine.username`           |
| "Currency mismatch."     | Pass `convert_to: "USD"` to convert with the app's rates, or filter to one currency  |

### 7.5 Pagination, ordering and truncation

Every list route takes `limit`, `offset` (or `cursor` where upstream pages by cursor) and `order`;
every one has a hard cap.

| Argument | Default | Cap   | Notes                                                                         |
| -------- | ------- | ----- | ----------------------------------------------------------------------------- |
| `limit`  | 200     | 5,000 | **Clamped, never rejected**                                                   |
| `cursor` | —       | —     | the transaction list's; wraps upstream's `max_time` time-sequence id (§10.3)  |
| `order`  | route   | —     | `field` or `-field`; only fields the route documents                          |

When a cap bound the result: `meta.truncated: true`, `meta.limitApplied: 5000` and, for the
transaction list, `data.nextCursor`. Upstream's `transactions/list.json` pages 50 at a time
(`count` 1–50); the plane walks upstream's cursor internally up to `limit`, so a caller asking for
500 rows makes one call, not ten.

**Ordering is always explicit and always total.** Every default order ends with a tie-break on `id`.
Transactions order by `transactionTime` (unix milliseconds, which is unique per user in
ezBookkeeping — it doubles as the time-sequence id) and then `id`.

### 7.6 Idempotency

- Every `GET` is idempotent and safe.
- Every `POST` that creates something accepts an optional `idempotency_key` (≤ 128 chars). A repeat
  within the process lifetime returns the **original** response with `meta.replayed: true`. This is
  mapped onto upstream's own duplicate checker: the plane passes the key as the `clientSessionId`
  upstream's `TransactionCreateRequest` already carries, so upstream's
  `[duplicate_checker] duplicate_submissions_interval` protection applies to machine writes too.
- A delete of something already gone is `ok: true` with `deleted: 0`, not a 404, so a retry loop
  terminates.

### 7.7 Request shape

`Content-Type: application/json` on every body-bearing call (multipart only on
`/ingest/file/plan`, which accepts a file). Bodies capped at **16 MiB** (a 12,000-row import batch is
about 3 MiB). Unknown top-level fields are **rejected**, not ignored — a typo'd `start_date` that
silently means "no filter" is how someone recategorises a decade.

**Every call carries a timezone.** Upstream's list and statistics handlers require
`X-Timezone-Offset` or `X-Timezone-Name` (`pkg/core/context_web.go`). The plane accepts
`X-Timezone-Name` from the client and otherwise uses the resolved default (§17.4), and **echoes the
zone it used in `meta.timezone`**, because "September" means a different set of transactions in
Los Angeles than in London.

## 8. Tiers, capabilities and negotiation

### 8.1 Three tiers

| Tier      | Server switch                  | What it is for                                                                                          |
| --------- | ------------------------------ | ------------------------------------------------------------------------------------------------------- |
| **read**  | always on                      | everything that computes and returns                                                                    |
| **write** | `EZBK_MACHINE_ALLOW_WRITE=1`   | changes the books: transactions, accounts, categories, tags, templates, rates, imports, undo            |
| **admin** | `EZBK_MACHINE_ALLOW_ADMIN=1`   | can lose data or change the install: every delete, clear-data, hide-with-cascade, key rotation, tokens  |

Admin is a separate switch and not "write plus". Write is "I intend to let a program edit my books
this week"; admin is "I am doing surgery right now and I am watching". **The MCP is never given the
admin tier** — with ONE exception the operator asked for: `DELETE /transactions/bulk`, behind
mcp.mdx §9.5b's `ezb_delete_transactions` (ids only, previewed, confirmed, undoable). Every other admin
route refuses the MCP (it identifies itself with `X-Ezbk-Client: ezbookkeeping-mcp/…`, and such a
route receiving that client answers `forbidden` even when the tier is on — a header is not
authentication, so this is a second fence, not the first), and the admin tier must be on for the
exception too. Both have their own tests.
The allow-list in code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/mount.go` — `mcpAdminRoutes`.

The switches are read from the server's environment at boot, set by `just run`'s caller or by
`ezbk up --allow-write`. They are **not** `.ini` keys: `conf/ezbookkeeping.ini` is upstream's file and
is checked in; a write switch that could be committed as `true` is a write switch that eventually is.

### 8.2 The client's switch is separate

The server's tier is necessary and not sufficient. `ezbk` requires `--write` on the call (cli.mdx
§7.1) and the MCP requires `EZBKMCP_ALLOW_WRITE=1` plus a per-call confirm (mcp.mdx §9.7). The plane
does not trust either client — **it enforces its own half.**

### 8.3 `GET /capabilities` (LOCKED)


**The table is generated from the same array the router is built from** (`routes.go`
`var ROUTES`). There is no second list. A test walks every published entry and asserts it answers
rather than falling through to the terminal 404.

**`upstreamFeatures` matters here in a way it did not for Actual.** ezBookkeeping switches whole
families on and off in its `.ini` — import (`[data] enable_import`), export, pictures, scheduled
transactions, custom icons. A route whose upstream feature is off is published with
`status: "disabled_upstream"` and answers `forbidden` naming the `.ini` key, so a client says _"import
is switched off in conf/ezbookkeeping.ini `[data] enable_import`"_ rather than surfacing a 404.

### 8.3a `status` — `live`, `planned`, `disabled_upstream` (LOCKED)

`live` means implemented. **`planned` means mounted, tiered and gated, with a handler that refuses
`not_ready` naming the phase that will build it** — so the gate ladder in front of a route is
integration-tested from P0. `disabled_upstream` is above.

## 9. The write protocol

### 9.1 The switches and the token (LOCKED)

Four things must be true before one transaction changes:

1. `EZBK_MACHINE_ALLOW_WRITE=1` on the server.
2. The client's own switch (`--write`, or `EZBKMCP_ALLOW_WRITE=1`).
3. `dry_run: false` in the call.
4. `confirm_token` echoing the token the matching dry run or plan returned.

Plus a ceiling: `max_changes`, default **200**, and a refusal over it **reports the real count** — as
`409 conflict` with `details.would_change`, `details.max_changes` and the change counts. There is no
`too_many_changes` code on this wire; the MCP mints one from that shape (mcp.mdx §12.3).

Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/confirm.go` — the ceiling check in the apply path

### 9.2 `dry_run` is the default, and the preview is the write (R4)

Every write route accepts `dry_run`, and **it defaults to `true`**. A call with no `dry_run` changes
nothing and returns what it would have done.

**How the preview is produced — honestly, for this app.** Actual Budget's importer takes a
`dryRun` flag natively. ezBookkeeping's services do not, and they open their own `xorm` sessions,
so "run it inside a transaction and roll back" is not available without editing upstream services.
The plane therefore produces previews in two sanctioned ways, and every write route's entry says which
it uses:

| Mode           | How                                                                                                                                                  | Used by                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| **resolve**    | The route's handler runs every validation and resolution step the write runs — names to ids, filter to row set, the upstream request object built — and stops one call short of the service write. The preview is the **resolved change set**: the exact ids and the exact before/after of every field. | every single-entity and bulk write        |
| **parse**      | For imports, upstream's own parse step (`TransactionParseImportFileHandler`'s converter call) **is** a preview: it turns a file into transactions without writing. The plan is its output plus our de-duplication verdict (§14.5). | `/ingest/*/plan`, `/ingest/file/plan`     |

Both obey the rule that matters: **the apply recomputes the change set through the same code and
compares its fingerprint to the token's** (§9.3). A preview is never produced by a second function
that predicts the first — the `resolve` step is literally the write handler's own first half,
factored so the second half is a separate call.

**Rejected: a `predictChanges()` function.** A second implementation that guesses what the first one
will do disagrees at exactly the edges that matter — a transfer's second row, a sub-account's parent
balance, a hidden category — and surfaces as a plan that says 117 and an apply that does 131.

The routes that have **no** `dry_run`, and say so in their schema: `POST /undo` (the preview is the
thing itself, and it returns what it undid).

### 9.3 The confirm token

A dry run returns:

```jsonc
{
  "ok": true,
  "data": {
    "dry_run": true,
    "changes": { "create": 0, "update": 46, "unchanged": 0 },
    "preview": [ { "id": "3401855937219633152", "field": "categoryId", "from": "…", "to": "…" } ],
    "confirm_token": "cf_01J8…",          // opaque, 128 bits from crypto/rand, this process only
    "expires_at": "2026-09-21T19:11:02Z",  // 10 minutes
    "fingerprint": "sha256:7ab3…"          // of the exact change set
  }
}
```

- **Ten-minute expiry**, then `conflict` with the hint to re-plan.
- **The change set is recomputed at apply time and compared against `fingerprint`.** If the world
  moved — the operator edited a transaction in the browser, the scheduled-transaction cron fired — the
  token is refused with `conflict` and the _new_ counts.
- **The token is in-process only.** Not persisted, not derived from the key, gone on restart.
- A model cannot invent it. The write path _requires having read the preview_.

### 9.4 Batch

`POST /batch` takes an ordered list of write operations (from a closed `op` set published in
`/capabilities`) and applies them under one confirm token, one ceiling and one journal entry. **All
or nothing, honestly bounded:** upstream services commit per call, so the plane applies operations in
order and, on the first failure, **reverses the ones already applied through the undo journal**
(§9.6) and reports the index that failed and why. The response says `rolledBack: n`. The ceiling
counts changes, not operations.

### 9.5 Transfers, sub-accounts and the second row

Three ezBookkeeping facts every write route must respect, stated once:

- **A transfer is two database rows** (`TRANSFER_OUT` type 4 and `TRANSFER_IN` type 5, linked by
  `RelatedId`) but **one API transaction** (type 4). Every count in a preview counts API
  transactions; a preview that said "2 changes" for one transfer would be the plan that disagrees
  with its apply.
- **A parent account with sub-accounts** (`type` 2, currency `---`) holds no balance of its own.
  Writes targeting a parent account are `invalid_input` naming its sub-accounts.
- **Balance-modification transactions** (type 1) are an account's opening balance, not income. The
  plane never creates one except through account creation with an initial balance, and never lets a
  bulk write change a transaction's type to or from it.

### 9.6 Undo — built here, because the app has none

Actual Budget's plane reached loot-core's own undo stack. **ezBookkeeping has no undo stack** — the
browser's delete is a soft delete with no "restore" button, and an edit overwrites. So undo is the
one feature this plane must **build**, and it is built narrowly and honestly:

- **The journal.** Every machine-plane write appends one entry to `machine_journal` (a table owned by
  `pkg/machine`, §4.1) holding: the route, the bound uid, the client, the timestamp, and **the
  inverse** — for a create, the created ids; for an update, the full prior state of every field it
  changed; for a bulk re-categorise, each row's prior `categoryId`; for an import, the created ids
  and the `machine_import_record` rows it wrote.
- **`POST /undo`** applies the inverse of the most recent un-undone journal entry **for this bound
  user**, inside the same write tier, and returns a description of what it reversed. `POST /redo`
  re-applies it. `GET /journal` lists recent entries (route, when, counts — never amounts).
- **Undo reverses machine-plane writes only.** It cannot undo something done in the browser, and it
  says so in its description and in `/capabilities`. Before reversing, it checks every row it will
  touch still matches the state the journal recorded **after** the write; if the operator has since
  edited one in the browser, undo refuses with `conflict` naming the row rather than overwriting a
  human's later edit.
- **Undoing a create soft-deletes** through the same service call the UI's delete makes. That is a
  delete, and deletes are admin-tier — the single sanctioned exception: undo may delete **only rows
  its own journal created**, and a test asserts it can reach no other row.
- **A conversion into transfers** (§10.3.2) journals one `txn.unconvert` op per request: each
  item's transfer (id and state), its originals (full prior state) and the import records it
  re-pointed. Undo checks every item first, then re-creates the originals (new ids), points the
  records back at them and deletes the transfers; no redo is recorded.
  In code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_transfers.go` — `xferExecUnconvert`.
- Undo is **write**-tier, built in the same phase as the first write (P5), never later — the most
  valuable route on this plane for an operator who has just let an agent write.

Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/journal.go` — `Record()`, `Undo()`, `Redo()`

### 9.7 What writes never do

- **Never delete without the admin tier** (except undo's own creations, above).
- **Never write outside the database, the staging directory and the log directory.** The only
  filesystem writes this plane performs are under `{STATEMENTS_ROOT}/.ezbk-staging/` (§14.3) and
  `~/T/_ezbookkeeping/` (audit).
- **Never invent a value.** No plug transaction hidden inside another row, no guessed category, no
  rounded amount, no exchange rate the app did not supply.
- **Never touch upstream's tokens** — no route mints, lists or revokes a JWT except the admin-tier
  `/admin/sessions` family, which the MCP cannot reach.

  `allow_type_change`, which changes the row's major category with it (§10.3.1).

#### 10.3.1 Categorisation: major category, group, sub-category

The operator thinks in three levels, and the plane names them the same way everywhere: the **major
category** is the category type (Income, Expense, Transfer — also the transaction's type), the
**group** is the primary category, and the **sub-category** is the secondary category a transaction
holds. A **category path** `Type > Group > Sub` (e.g. `Expense > Food & Drink > Food`) names all
three and is never ambiguous; `Group > Sub` and `Sub` are accepted when they are. Every category
name argument on the plane accepts a path (`category_name` on the transaction routes, `:id` and
`parent_name` on the category routes).
Path parsing and resolution against the row's own type is done in code:
`~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_categorize.go` — `catzParsePath`, `(*txnLookup).resolveCategoryFor`.

Imported rows land in a fallback category (`Imported > Uncategorized`, one per type). Three routes
serve whoever categorises them — usually an agent through the MCP:

- **`GET /transactions/uncategorized` — the work queue.** Every row in the fallback categories,
  grouped by normalised payee (the payee leaderboard's normaliser, §12), largest group first. Each
  group carries its ids (capped by `ids_per_group`, with `idsTruncated`), per-type counts, signed
  per-currency totals, first and last date, accounts, up to five raw descriptions, three sample rows,
  and a **suggestion**: what categorised rows with the same payee were given — `votes` of `of`, the
  `basis` (`same_payee`, or `payee_prefix` on the first two words) and up to three alternatives,
  restricted to categories the group's rows could take without a type change. A suggestion is a
  count, not a verdict. Groups leave the queue as they are categorised, so a categoriser re-reads
  from offset 0 after each write. Balance modifications never appear.
  Grouping and suggestions in code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_categorize.go` — `catzHandleQueue`, `catzGroupQueue`, `(*catzHistory).suggest`.
- **`POST /transactions/categorize` — per-row assignments.** Many categories in one previewed,
  confirmed, journalled write of up to 5,000 rows; each id may appear in one assignment only. A path
  without a type resolves against each row's own type first, so `Imported > Uncategorized` means the
  expense one for an expense row. A category of another type is refused naming the row unless
  `allow_type_change` is set; then income ↔ expense flips the direction and keeps account and amount;
  income or expense → transfer needs `counter_account` (an expense pays into it, an income came from
  it; `counter_amount` when the currencies differ); transfer → expense keeps the source side and
  transfer → income the destination side. `skip_invalid` lists refused rows under `preview.skipped`
  and changes the rest; `summary_only` drops the per-row diff and keeps `preview.byCategory`. Rows
  that only change category go through `TransactionBatchUpdateCategoriesHandler` (one call per target
  category); type changes go through `TransactionModifyHandler` row by row; one journal entry undoes
  the batch.
  The row transitions in code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_categorize.go` — `catzTargetState`; the write in `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_transactions.go` — `txnApplyBulkStates`.
- **`POST /categories/ensure` — the taxonomy.** `paths[]` of full `Type > Group > Sub` paths; only
  the missing groups and sub-categories are created (names match ignoring case), existing ones are
  returned with their ids, a new sub-category takes its group's colour and icon. One journal entry
  deletes what it created.
  In code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_categorize.go` — `catzPlanEnsure`, `catzHandleEnsure`.

A category's own type cannot change (upstream forbids it); moving a group to another major category
is `categories/ensure` under the new type followed by `transactions/categorize`.

#### 10.3.1a Round trip by id: export with ids, categorise from the file

Upstream's CSV/TSV export has no id column, so a file pulled out of the books cannot be written back
to the same rows. `GET /transactions/export?with_ids=true` renders the plane's own file instead, from
the same filtered walk `GET /transactions` uses (one row per API transaction; a transfer once; at most
50,000 rows, past that `invalid_input` asks for start/end). Columns, in this order:

`ID, Date, Type, Category Path, Category, Sub Category, Account, Currency, Amount, Amount Hundredths,
Counter Account, Counter Amount, Tags, Description, New Category, New Counter Account, Rule`

- `ID` is the database primary key, always first, always a decimal string (a spreadsheet must keep it
  as text: 18 digits do not survive a float).
- `Category Path` is `Type > Group > Sub` (§10.3.1). `Amount` is signed — money out of the row's
  account is negative — and `Amount Hundredths` is the same figure as an integer.
- `New Category`, `New Counter Account` and `Rule` are empty: a categoriser fills them. The MCP's
  `ezb_set_transaction_categories_csv` reads the file back, groups rows by (New Category, New Counter
  Account) into `assignments[]` and sends ONE `POST /transactions/categorize` — so the whole round
  trip is two calls and every row is found by its primary key.
- A row that becomes a transfer may name a HIDDEN counterpart (a family member's account, "Own-Account
  Clearing"). Upstream refuses to modify a transaction in a hidden account, so every bulk write —
  and its undo — makes the hidden accounts it touches visible for the moment of the write and hides
  them again, whether the write failed or not (the same rule §10.3.2's conversion follows).
  In code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_transactions.go` — `txnWithHiddenVisible`, used by `txnApplyBulkStates` and `txnExecRestore`.
Implemented in `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/export_rows.go` — `txnExportWithIds`, `exportRowsRender`;
the switch in `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_transactions.go` — `txnHandleExport`.

#### 10.3.2 Own-account moves as transfers

A statement import writes one income/expense row per statement line, per account (§14). Two kinds of
rows then inflate every income and expense total — the home page, the statistics, `/analytics/*`:

- **A move between two of the operator's own accounts** (a card payment from checking, checking →
  savings) arrives as an EXPENSE in one account and an INCOME in the other. It is ONE move and
  becomes ONE ezBookkeeping transfer, which upstream's statistics already leave out.
- **A row that is not income or spending at all** — an investment account's monthly change in
  printed market value, or a one-sided move whose other side is not a ledger in these books —
  becomes a transfer against a named counterpart account (typically a hidden one), so it stops
  counting while the operator's account balance stays exactly the same.

Two routes serve this. Both work on rows that already exist, so they apply equally to imported and
hand-entered rows.

**`POST /transactions/transfer-candidates` (read, composed).** Finds pair items for the conversion
without writing anything.

Request body (every field optional):

```json
{ "account_ids": ["…"], "account_names": ["Northbank Checking ••4021"], "start": "2026-03-01", "end": "2026-03-31",
  "window_days": 4, "require_hint": true, "limit": 1000 }
```

- `account_ids` / `account_names`: the accounts to search (a parent expands to its sub-accounts);
  default every visible leaf account. Both rows of a candidate must be in this set.
- `start` / `end`: a candidate needs at least one side inside the range; the scan reaches
  `window_days` beyond each end so a counterpart just outside still counts.
- `window_days`: default 4, 0–31. `require_hint`: default true. `limit`: how many `pairs` (and,
  separately, `ambiguous` groups) come back, default 1000, at most 5000; `counts` always cover
  everything found.

A **candidate** is an EXPENSE row in account A and an INCOME row in account B ≠ A, same currency, same
absolute amount, at most `window_days` calendar days apart. A **hint** (required unless
`require_hint: false`) is either
- a comment carrying the OTHER account's last four digits as their own number — the last four are
  the trailing run of at least four digits of the account NAME (`Checking ••4021`, `Card x4021`,
  `…4021`, `*4021`, `Savings 99994021` → `4021`); the comment may write them `x4021`, `...4021`,
  `*4021`, `••4021` or `#4021`, but never inside a longer number; or
- a comment containing a word of the documented transfer vocabulary, matched ignoring case on word
  boundaries: `PAYMENT`, `AUTOPAY`, `AUTO PAY`, `TRANSFER`, `XFER`, `EPAY`, `THANK YOU`, `CRD`,
  `CREDIT CARD`, `ONLINE PMT`, `FROM CHK`, `TO CHK`, `FROM SAV`, `TO SAV`, `DEPOSIT TRANSFER`.

Only **unambiguous** candidates — the expense has exactly one candidate AND the income has exactly
one — come back as `pairs`. Every other candidate belongs to an `ambiguous` group (a connected set
of rows and their candidates), listed whole, for a human to choose. Output order is deterministic
(expense date, then ids).

Response `data`:

```json
{ "pairs": [ { "expense": {…row}, "income": {…row}, "dayGap": 2,
               "hints": [ {"kind": "last_four", "digits": "7788", "comment": "expense", "account": "Meridian Card ••7788"},
                          {"kind": "vocabulary", "term": "THANK YOU", "comment": "income"} ],
               "item": { "id": "<expense id>", "counter_id": "<income id>" } } ],
  "ambiguous": [ { "expenses": [{…row}], "incomes": [{…row}],
                   "candidates": [ {"expenseId": "…", "incomeId": "…", "dayGap": 0, "hints": […]} ] } ],
  "counts": { "pairs": 1, "ambiguousGroups": 0, "ambiguousCandidates": 0, "candidates": 1,
              "scannedExpenses": 212, "scannedIncomes": 64, "pairsReturned": 1, "ambiguousGroupsReturned": 0 },
  "scanTruncated": false,
  "filter": { "accountIds": ["…"], "start": "2026-03-01", "end": "2026-03-31", "windowDays": 4, "requireHint": true, "timezone": "America/Los_Angeles" } }
```

A row is `{id, date, typeName, accountId, accountName, amount, currency, comment, categoryId,
categoryName}`. Rows are walked through the same upstream list `GET /transactions` walks, one scan
per type capped at 5000 rows; past it `scanTruncated` is true and `meta.truncated` is set — narrow
with `start`/`end` or accounts.
Detection in code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_transfers.go` — `xferHandleCandidates`, `xferFindCandidates`, `xferLastFour`, `XferTransferVocabulary`.

**`POST /transactions/convert-to-transfer` (write, dry-runnable, composed).** The write protocol of
§9 exactly: `dry_run` (default true), `confirm_token`, `max_changes`.

```json
{ "items": [ { "id": "3844…0384", "counter_id": "3844…0385" },
             { "id": "3844…0391", "counter_account_name": "Market Value" },
             { "id": "3844…0392", "counter_account_id": "3844…0660" } ],
  "comment_mode": "both",
  "transfer_category_id": "…", "transfer_category_name": "Moves > Internal",
  "dry_run": true, "confirm_token": "cf_…", "max_changes": 200 }
```

- **Pair item `{id, counter_id}`.** Both rows are INCOME or EXPENSE (never a transfer or balance
  modification), one expense and one income, in different accounts, with equal amounts when the
  currencies agree (when they differ each side keeps its own amount as `sourceAmount` /
  `destinationAmount`). Result: ONE transfer, source = the expense's account, destination = the
  income's account, time and utc offset = the expense's. The destination account's running balance
  therefore moves from the income's posting day to the expense's for the days between
  (`preview.items[].destinationDateShift` says so); its final balance is unchanged. Comment = the
  expense's comment, plus ` ⇄ ` and the income's when `comment_mode` is `both` (the default) and they
  differ (`out`: the expense's alone; cut to 255 characters with a warning). Tags = the union (at most
  10). Geo = the expense's, else the income's.
- **Single item `{id, counter_account_id | counter_account_name}`.** An expense row in account A
  becomes a transfer A → counter; an income row in A becomes counter → A. Same amount, time, comment
  and tags. The counter is a different, leaf, same-currency account (resolved like every account
  argument); it may be hidden.
- **The transfer category.** A transfer needs a transfer-type sub-category. `transfer_category_id` /
  `transfer_category_name` name one; otherwise the plane takes the first visible transfer
  sub-category in display order. When the operator has none the call fails `not_found` with a hint
  naming `POST /categories` (type transfer) — it never creates one silently.
- **Refused, all problems at once** (`details.problems[]` of `{index, id, code, problem}`; the call is
  `not_found` when every problem is a missing row, else `invalid_input`): a row that does not exist
  (deleted since), a row that is already a transfer (a TRANSFER_IN id counts), a balance
  modification, two rows of the same type, the same account, unequal same-currency amounts, a
  single's counter in another currency or the row's own account, rows with pictures (a conversion
  would not carry them), more than 10 merged tags. An id named twice anywhere in one request is
  refused up front with `details.duplicates`, and so is an item with both or neither of `counter_id`
  and `counter_account_*`.

The **preview** (`preview.items[]`, one per item) shows `kind` (`pair` | `single`), `before` (the
rows as they are: account, type, amount, date, comment, category), `after` (the transfer), `dayGap`,
`importRecords` (how many statement import records follow the conversion) and `balanceEffect`: per
account, its `before` and `after` effect and `netChange`. The plan asserts `netChange` is 0 for every
account — except a single item's counter account, whose row is marked `counterpart: true` because
taking the other side of the move is its purpose — and refuses the item otherwise.
`preview.hiddenAccounts` lists hidden accounts the conversion touches, `preview.transferCategoryId`
/ `transferCategoryPath` the category used. `changes` is `{convert, create, delete}`; the ceiling
(`max_changes`) counts the ORIGINAL rows converted (a pair is 2, a single 1).

The **apply**, item by item: create the transfer through upstream's `TransactionCreateHandler`,
delete the originals through `TransactionDeleteHandler`, then re-point every `machine_import_record`
row (§14.6) whose `transaction_id` named an original at the transfer's id — so a later statement
re-plan still reports those statement rows as `already_present`, never `new`. A failure part way
through an item rolls that item back (the originals are re-created with new ids and their records
follow them) and the call fails naming `failedIndex`; items before it stand and are journaled.
Upstream refuses to add a transaction to, or delete one from, a **hidden account**, so a hidden
account an item touches is made visible for the moment of that item and hidden again afterwards.

Response `result`: `{ "converted": 2, "ids": ["<transfer id>", …], "items": [ {"index": 0, "kind":
"pair", "transferId": "…", "deletedIds": ["…", "…"], "recordsRepointed": 2} ] }`, plus
`journal_id` beside it.

**Undo** (`POST /undo`, `ezb_undo`, `ezbk undo`): the whole conversion is one journal entry with one
inverse op, `txn.unconvert` (§9.6). It checks every item first — each transfer unchanged since the
conversion, each original still deleted — so a refusal changes nothing; then, newest item first, it
re-creates the originals (new ids, same fields; pictures were refused up front), re-points the import
records at them, and deletes the transfer. Redo is not recorded: re-run the conversion instead.
In code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_transfers.go` — `xferHandleConvert` (resolve and plan), `xferBuildPair` / `xferBuildSingle` (the transfer), `xferBalanceRows` (the assertion), `xferApplyItem` (create, delete, re-point), `xferExecUnconvert` / `xferRestore` (undo).

#### 10.4.1 The category tree as one document — `GET /categories/tree`

A categoriser — an agent, a script, the operator in a text editor — needs the whole list of choices
before it picks one: every major category (income, expense, transfer), every group under it, every
sub-category under that. `GET /categories` answers the tree too, but as the app's full category rows;
`/categories/tree` answers exactly the choices, in display order, and renders them **on the server** as
one YAML document, so no client assembles or re-sorts them.

The JSON envelope carries both: `data.groups[]` (`name`, `type`, `id`, `hidden`, `subcategories[]` of
`name`, `id`, `hidden`), `data.counts` (`groups`, `subcategories`), `data.generatedAt`, and
`data.yaml` — the same tree as text. `format=yaml` answers the document alone
(`application/yaml`), for curl and a text editor. Hidden groups and sub-categories are left out unless
`include_hidden`; `type` narrows to one major category.

```yaml
app: ezbookkeeping
generated_at: "2026-09-21T22:00:00Z"
counts:
  groups: 2
  subcategories: 3
groups:
  - name: Food & Drink
    type: expense
    id: "3401855937219633200"
    hidden: false
    subcategories:
      - name: Groceries
        id: "3401855937219633201"
        hidden: false
```

The shape is shared with the sister apps' planes (Actual Budget's `GET /categories/tree` and Firefly
III's), so one categoriser reads all three: `app`, `generated_at`, `counts`, `groups[name, type, id,
hidden, subcategories[name, id, hidden]]` — an app without a type or a hidden flag leaves that key out.
The document lists choices, never amounts. Surfaces: MCP `ezb_get_category_tree` (mcp.mdx §9.5), CLI
`ezbk categories tree` (cli.mdx §6).

Builds the tree, in the list route's order, and renders the YAML in code:
~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_categorize.go `catzHandleTree`, `catzBuildTree`, `catzTreeYAML`

### 11.1 The deliberate omissions, stated as decisions

1. **Password, email, avatar, 2FA, OAuth2 links** — identity and credentials. A program changing
   them can lock the operator out; the browser, with its confirmation flows, is the only right place.
2. **Generating upstream API or MCP tokens** — that would hand a program a full-access bearer
   credential that travels (§2.2). If the operator wants one, `ezbookkeeping userdata
   user-session-new` is theirs to type.
3. **LLM recognition** (`/llm/transactions/recognize_*`) — it sends the operator's text or receipt
   image to a configured third-party model. The plane has no egress (§19.2), and a program choosing
   to upload a receipt is a program exfiltrating one.
4. **Pictures and custom icons** — binary uploads with their own storage and cleanup lifecycle;
   deferred to P9, not refused. Metadata (whether a transaction has pictures) is readable now.
5. **Registration and other users** — the plane serves one bound user (§6); user management is
   `ezbookkeeping userdata …`, upstream's own admin CLI.

Every other cell is a route, and a new UI feature upstream that this table cannot absorb is a change
to this spec before it is a change to any client.

of big-integer strings, per currency**, and `statistics/trends.json` the same per month. The
**grouping** (secondary into primary category), the **currency conversion** into the default
currency, the **percentages**, the **top-N** and the **"other"** bucket all happen in the browser, in
`src/stores/statistics.ts` (e.g. line 572, `exchangeRatesStore.getExchangedAmount(...)`).

That is fine for a browser and fatal for us: the thin-client rule says a client never sums, and
"what did I spend on groceries this year" is a sum — and in a multi-currency book it is a sum **plus
a conversion**. So the grouping and conversion move here, into Go, once. Three consequences, all
intended:

- The CLI, the MCP and (eventually) the browser agree on a total because there is one implementation.
- A model never does arithmetic on money, and never converts currencies in its head.
- A ten-year aggregate is one call returning 120 rows, not 12,007 rows the caller must reduce.

### 12.3 The rules these obey

- **Every figure is integer hundredths with its currency**, every count an integer. No percentages
  as floats — a share is returned as its two integers (`amount`, `total`) and the presentation layer
  divides.
- **Transfers are excluded by default.** A transfer from Checking to Savings is not spending.
  `include_transfers: true` exists, and the response echoes which it did.
- **Balance modifications are always excluded from income and expense.** An account's opening balance
  is not income, and counting it is how a tracker reports a record month the week an operator sets up
  their accounts. There is no argument to include it.
- **Hidden accounts are excluded by default**, and the response says so.
- **Per currency unless `convert_to`.** Without it, every series is returned per currency and no
  total crosses a currency boundary. With it, every converted figure carries the rate (§13.2).
- **Every response carries its own provenance**: resolved date range, timezone, the account ids
  actually included, the filters applied, the row count, and — if converted — every rate used.
- **Detectors are not oracles.** `/recurring` and `/anomalies` return the evidence (the occurrences,
  the trailing mean, the deviation) so the caller can show its work.
- **One implementation of grouping.** Primary-category roll-up, top-N and the "other" bucket live in
  `pkg/machine/handlers/analytics.go` and nowhere else.

### 12.4 The charting it feeds (the direction of this fork)

This fork intends to grow **more charting** than upstream ships — month-over-month category bars,
net-worth lines, runway, tag breakdowns, multi-currency views. That work lands in this order, and the
order is the point:

1. **The numbers first, here.** Every chart this fork will ever draw is a route in §12.2 before it is
   a pixel. The response shape is chart-ready on purpose: `series[]` of `{key, label, currency,
   points[{period, amount}]}` plus `provenance`.
2. **Then the terminal and the agent.** `ezbk analytics … --format csv` pipes a series into any
   plotting tool, and the MCP returns the same series a model can describe (or, in a surface that
   renders charts, hand over as data rather than a picture).
3. **Then the browser.** New Vue chart components call the **same** analytics routes through a
   browser-safe door (a JWT-authenticated `/api/v1` mirror of the analytics family, added then), so
   the chart the operator sees and the number the agent quotes are the same computation. What must
   never happen is a new chart that re-implements the sum in TypeScript beside `statistics.ts` —
   that is two implementations, and the day they disagree the operator trusts neither.

Code: `~/BGit/Bryan_git/ezbookkeeping/src/stores/statistics.ts` — upstream's in-browser grouping and conversion (exists today; the logic being moved)

## 13. Currencies — the rule this app adds

Actual Budget is single-currency, so its specs never needed this section. ezBookkeeping is not: every
account has an ISO 4217 currency, a user has a default currency, a transfer can cross currencies with
two different amounts, and the app keeps exchange rates from a configured provider
(`[exchange_rates] data_source`, European Central Bank by default) plus the user's custom overrides.

### 13.1 The rule (LOCKED — R11)

> **Every amount travels with its currency, and two currencies are never combined without a named
> rate.**

- Every amount field on the wire has a sibling currency field, or sits inside an object that has one.
  A bare `amount` with no reachable currency is a bug in the route.
- A list, a total, a ranking or a comparison that spans currencies is returned **per currency** unless
  the caller asked for conversion.
- "Largest expense" across a USD and a JPY account is not answerable without conversion, and the
  route says so rather than comparing 50,000 yen to 500 dollars as if they were numbers of the same
  thing.

### 13.2 Conversion (LOCKED)

`convert_to: "USD"` on an analytics route or `POST /exchange-rates/convert`:

- Uses **the app's rates only**: the user's custom rate for a currency if one exists, otherwise the
  provider's latest. Never a rate the caller supplied inline, never one a model remembered.
- **Names every rate used**, with its source (`custom`/`provider`), the provider name, and its
  `updateTime`.
- **States the limitation plainly.** ezBookkeeping keeps **latest** rates, not historical ones. A
  2019 euro expense converted today uses today's rate, and the response carries
  `rateBasis: "latest"` and a `note` saying historical figures are converted at the current rate. A
  caller that needs historical-rate accuracy is told it is not available, not handed a number that
  pretends otherwise.
- Rounds **once**, at the end, half-away-from-zero to hundredths, in `money.go`. Converting each row
  and summing the rounded rows is a different number from summing and converting; the plane sums in
  the source currency first, converts each currency's total once, and reports both.
- A currency with **no rate available** is not silently dropped from a converted total: it is
  returned in `unconverted[]` with its own per-currency figure, and `meta.partial: true`.

### 13.3 The default currency

`meta.defaultCurrency` (the bound user's) is on every response, so a client that renders a total
knows which currency the operator thinks in. It is a display preference, never a silent `convert_to`.

## 14. The ingest plane — statements into the books

The flagship, as in the Actual fork — but with one large difference that shapes everything below.

> **Actual Budget had an importer that decides duplicates. ezBookkeeping does not.** Its import
> (`POST /api/v1/transactions/import.json`) writes whatever rows it is handed; its only protection is
> `clientSessionId`, which stops the _same submission_ twice within five minutes, not the same
> transaction arriving in two files a month apart. So on this fork, **the machine plane is the
> duplicate authority**, and because it is, it is implemented exactly once, deterministically, with
> a durable record, and never by a model.

### 14.1 Two modes, because two kinds of tree exist

| Mode           | Input                                                                                                                        | What we do                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **`prepared`** | a tree that already holds importable files (`.ofx` / `.qfx` / `.qif` / CAMT `.xml` / MT940 / `.csv`) and a manifest          | read the manifest, hand each file to **ezBookkeeping's own converter**, dedupe, import |
| **`raw`**      | a tree of statement PDFs and text sidecars                                                                                   | extract → normalise to ezBookkeeping CSV → dedupe → stage → import             |

**`prepared` is primary and built first.** ezBookkeeping's converter shelf is wider than Actual's:
`ofx`, `qfx`, `qif_ymd`/`qif_mdy`/`qif_dmy`, `iif`, `camt052`, `camt053`, `mt940`, `gnucash`,
`firefly_iii_csv`, `beancount`, custom delimiter-separated and Excel files with a column map, and
several regional app formats (`pkg/converters/transaction_data_converters.go`
`GetTransactionDataImporter()`). A real archive is usually already prepared, and re-extracting from
PDF what an OFX `FITID` already carries is strictly worse.

`raw` is for statements that only ever existed as paper; its output is **ezBookkeeping CSV**
(`ezbookkeeping_csv`), so even the raw path ends in the app's own parser.

**The prepared tree is not ours.** It is audit evidence produced by whatever pipeline the operator
ran, and this plane treats it as **strictly read-only** — never writes into it, never moves a file in
it, never rewrites its manifest.

### 14.5 Two layers of de-duplication

**Layer one, the statement level.** The same month scanned twice under two filenames is one
statement. Grouping is on `(entity, institution, last4, statement_period)` read from _inside_ the
document, never from the directory name. Identical bytes → `duplicate_identical`. Different bytes,
same period → ranked by a fixed rule chain (more rows; wider coverage; better source; newer mtime;
lexicographically first path — deterministic on every machine), the loser `superseded`, both recorded.
Two statements that disagree about a _transaction_ → `conflict`, which blocks that account-month and
names both files.

**Layer two, the transaction level — the `import_id`.**

- In **prepared** mode, if the converter surfaces the bank's own id — OFX/QFX `FITID`
  (`pkg/converters/ofx/ofx_data.go`, field `TransactionId` tagged `xml:"FITID"`), CAMT `AcctSvcrRef`
  / `NtryRef`, MT940 reference — **that is the id, prefixed by its account key**. We never mint our
  own over the top of a bank's.
- Otherwise (CSV, QIF, raw) we mint:
  `sha256(account_key ‖ date ‖ amount_hundredths ‖ currency ‖ normalised_description ‖ ordinal)[:32]`,
  where `account_key` is `{entity}/{institution}/{last4}` (not the ezBookkeeping account id, so a
  deleted-and-recreated account still matches), and `ordinal` is the tie-group index **within the
  merged account-month** — so two genuine $5.00 coffees on the same day at the same shop get ordinals
  0 and 1 and both import, and a cycle-dated card whose 15th-to-14th statements feed one calendar month
  from two files does not collapse two real transactions into one. (Actual's cli.mdx §10.6a is the long
  form of why the scope is the merged account-month; the rule is carried over unchanged.)

Category, tags and comment are deliberately **not** in the hash — those are things the operator changes
after import, and an id that changed when they did would re-import every edited row.

### 14.6 The durable record — `machine_import_record` (LOCKED)

ezBookkeeping's `Transaction` has no `imported_id` column, and we will not add one to upstream's table
or smuggle one into `comment` (the operator's field). So the plane keeps its own table:

| Column            | Holds                                                            |
| ----------------- | ---------------------------------------------------------------- |
| `uid`             | the bound user                                                   |
| `import_id`       | §14.5 — unique per `uid`                                         |
| `transaction_id`  | the ezBookkeeping transaction it became                          |
| `account_key`     | `{entity}/{institution}/{last4}`                                 |
| `source_file`     | path relative to the statements root                             |
| `run_id`          | the ingest run                                                   |
| `created_unix_time` |                                                                |

**The plan asks this table, and only this table, "does this row already exist?"** — one
implementation, the authority on this fork.

**A deletion is a decision, and it is respected (LOCKED).** When the operator deletes an imported
transaction in the browser, ezBookkeeping soft-deletes the row; our record still points at it. The
next run finds the `import_id`, sees the transaction is deleted, and counts it
`already_present_deleted` — **not re-imported**. This is Actual's `reimportDeleted: false` lesson
applied at birth rather than retro-fitted: an import that resurrects deleted rows every month is an
import nobody runs twice. The operator who wants one back runs `ezbk statements apply
--reimport-deleted --yes`, which names every row it would resurrect first. No MCP tool can do it
(mcp.mdx §11.3): the argument is published by `/ingest/plan` and `/ingest/file/plan` and accepted only
from the CLI's schemas.

**An undo is not a deletion (LOCKED).** `POST /undo` of an import run deletes the transactions the run
created **and removes their `machine_import_record` rows** — each only while it still points at the
transaction the run made, so a record a later run re-pointed is left alone — and re-points an accepted
match's record back at the prior transaction. The next plan therefore counts those rows as **new**
again, which is what undoing an import means. The browser delete above leaves the record standing and
the row stays `already_present_deleted`. The two are different decisions and the table records them
differently.

Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/ingest_apply.go` — `ingUndoImport()`, the import run's inverse
Code: `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/ingest_record.go` — `ingDeleteRecords()`, `ingRelinkRecords()`

**Fuzzy matching against hand-entered rows.** An operator often types a transaction in by hand and the
statement arrives later. The plan reports, per statement row with no `import_id` match, any existing
**un-recorded** transaction in the same account with the same amount and currency within ±3 days as a
`possible_match` — and **does not decide**. Possible matches are excluded from the apply by default
and listed for the operator; `accept_matches[]` on the apply links a named statement row to a named
existing transaction (writing the record, creating nothing). A statement row is never fuzzy-matched to
another statement row: those match on `import_id` or not at all.

### 14.7 Mapping categories and accounts (LOCKED)

ezBookkeeping requires a secondary category on every income and expense transaction, and its
converters bring category **names** from the file (or none). The UI's import dialog makes the human
map them. The plane does the same, explicitly:

- **Accounts** map through the statements map (§14.4 `/ingest/map`), written by `/ingest/accounts/apply`.
- **Categories** map by exact name to the bound user's secondary categories of the right type.
  Anything unmatched goes to `_unmapped.csv` and the plan's `unmapped[]`, with every row count.
- **A fallback is explicit.** `fallback_category_ids: {expense: "…", income: "…"}` names where
  unmatched rows land. Without it, a plan with unmapped categories **blocks** that account and says
  so. The plane never picks a category; `/analytics/import-fallout` later lists what went to the
  fallback, so it can be re-categorised deliberately.
- **Transfers between two mapped accounts** in one import (a card payment appearing in both the
  checking and the card statement) are detected by equal-and-opposite amounts on the same date across
  two mapped accounts and **reported as `transfer_candidates[]`, never merged automatically**. Accepting
  one (`accept_transfers[]`) imports a single ezBookkeeping transfer instead of an expense in one account
  and an income in the other — the double-count that makes a tracker report spending twice.

### 14.8 Plan and apply are one path

`/ingest/plan` parses every file through `pkg/converters`, runs both dedupe layers, consults
`machine_import_record`, applies the maps, and returns per account: rows parsed, collapsed, already
present (and already present but deleted), possible matches, transfer candidates, unmapped, **new** —
plus a `confirm_token` whose fingerprint covers the exact set of new rows. `/ingest/apply` **recomputes
all of it** and refuses with `conflict` and the new counts if the fingerprint moved; then submits the
new rows through the same service path `TransactionImportHandler` uses (in batches, reporting progress),
writes `machine_import_record` and the journal entry, and returns the created counts per account.

**The comment field.** The statement's description goes into the new transaction's `comment` — that is
where ezBookkeeping's own importers put it, and it is the only text field a transaction has. But it is
written **only on create**. A re-run never updates the comment of an existing row, because by then the
operator may have edited it, and an import that overwrites a note a human typed has destroyed the only
data in the row a human authored. A test writes a comment, re-runs, and asserts it survives byte for
byte.

**An empty statement is a statement.** A file whose converter answers "not found transaction data" (an
OFX with an empty `BANKTRANLIST` — a month with no activity, a dormant account) counts as a primary
statement with zero rows and a warning, never as an `unreadable_file` conflict.
Code: `ingIsEmptyFile()` in `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/ingest_plan.go`.

### 14.9 What ingest never does

- Never writes, moves, renames or deletes anything under `{ROOT}` outside the staging directory.
- Never deletes a transaction. Ingest is additive.
- Never guesses a category, an account, a currency, or a QIF date order.
- Never invents a date, an amount, or a balancing row. An unreadable row is named in `_conflicts.csv`
  and counted.
- Never uploads a statement anywhere — including to the LLM recognisers upstream offers.

### 14.10 Categorising imported rows from the statement file — `POST /ingest/categorize`

An OFX row carries no category, so an import lands every income and expense row in a fallback
category (§14.9: ingest never guesses one). The categories are decided afterwards, outside the plane,
and written into each account's **companion file** — the ezBookkeeping TSV next to the import
(import_formats.mdx §11.4a) with `Type` (the major category), `Category` (the group), `Sub Category`,
and a `FITID` column repeating the OFX row's bank id. This route gives the rows already in the books
those categories, importing nothing again.

| Argument                  | Meaning                                                                                 |
| ------------------------- | --------------------------------------------------------------------------------------- |
| `root`, `manifest_path`   | as §14.2; the manifest names each account's `file`, whose same-stem `.tsv` is the companion |
| `accounts[]`              | account keys, labels, paths or last-fours (default: every manifest account)            |
| `file`                    | one account's category file instead of its companion (`.tsv`, or a quoted `.csv`); exactly one account |
| `fallback_category_ids[]` | the categories rows may leave (a group means its sub-categories); default every sub-category named `Uncategorized` |
| `overwrite`               | also change rows already outside the fallback (default false)                          |
| `limit`                   | rows changed per call, default and cap 5000; `preview.remaining` counts the rest       |
| `summary_only`            | drop the per-row before/after from the preview                                         |
| `dry_run`, `confirm_token`, `max_changes` | §9.2                                                                   |

Per row: the file's `FITID` becomes the import id `{account_key}|FITID:{fitid}` (§14.5), the import
record names its transaction, and the transaction must still exist, must not be a balance modification,
and must hold the file's major category — a row the reclassify pass turned into a transfer is skipped
as `type_differs`, never converted back. A row outside the fallback is counted `already_categorized`
unless `overwrite`. The path `Type > Category > Sub Category` must exist: an unknown one is listed in
`preview.unknownCategories` with its row count and never created (create it with
`POST /categories/ensure`, then plan again). Everything else is exactly `POST /transactions/categorize`
(§9.8): one bulk plan, `preview.byCategory`, a confirm token over the change set, one journal entry
that `/undo` reverses. `changes` carries `update`, `unchanged` and one `skip_<reason>` count per reason
(`no_category`, `no_fitid`, `not_imported`, `transaction_gone`, `balance_modification`, `type_differs`,
`already_categorized`, `unknown_category`, `duplicate`, `over_limit`); `preview.skippedSamples` names
the first 50 skipped rows by account and line.

Re-running is safe by construction: changed rows leave the fallback, so a second plan finds `update: 0`,
and a category the operator set by hand is never overwritten without `overwrite`.

Reads the companion file, traces each FITID through `machine_import_record` and builds the plan in code:
~/BGit/Bryan_git/ezbookkeeping/pkg/machine/ingest_categorize.go `ingHandleCategorize`, `ingCatzParseFile`, `ingCatzFiles`
Plans and applies the category changes (shared with `/transactions/categorize`) in code:
~/BGit/Bryan_git/ezbookkeeping/pkg/machine/routes_categorize.go `catzPlanAssignments`, `catzApply`

## 15. Account provisioning from a manifest

### 15.1 `POST /ingest/accounts/plan` (read)

Reads the manifest and the bound user's accounts, and returns a per-row decision with its reasoning.
It **creates nothing**.

```jsonc
{
  "ok": true,
  "data": {
    "plan": [
      { "manifest": { "entity": "household", "institution": "Northbank", "label": "Checking_x4021",
                      "last4": "4021", "kind": "checking", "currency": "USD" },
        "action": "create",
        "proposed": { "name": "Household · Northbank Checking ••4021", "category": "checking",
                      "currency": "USD", "side": "asset" },
        "reason": "no existing account matched on last4 or name" },

      { "manifest": { "entity": "household", "institution": "Meridian", "label": "Retirement",
                      "kind": "brokerage", "currency": "USD" },
        "action": "create",
        "proposed": { "name": "Household · Meridian Retirement", "category": "investment",
                      "currency": "USD", "side": "asset" },
        "reason": "kind=brokerage → investment",
        "warnings": ["source is monthly aggregate, not per-trade"] },

      { "manifest": { "entity": "acme_llc", "institution": "Northbank", "label": "Card_x7734",
                      "last4": "7734", "kind": "card" },
        "action": "link",
        "existing": { "id": "3401855937219633152", "name": "Acme LLC Card" },
        "reason": "matched on last4 7734" }
    ],
    "summary": { "create": 24, "link": 3, "ambiguous": 0 },
    "confirm_token": "cf_01J8…"
  }
}
```

A manifest row with `opening_balance`/`opening_date` adds `"opening_balance": 123456, "opening_date": "2026-01-01",
"opening_time": 1767268799` to its `proposed` block and `balance`/`balance_time` to its change-set entry,
so the confirm token covers the opening balance too. A positive opening on a liability is warned about
(money owed is negative).

`action` is one of `create` · `link` · `skip` · `ambiguous`. **`ambiguous` never becomes a create** —
two accounts sharing a last4 across two entities is the normal case in a real archive.

### 15.2 The naming rule

Default `"{Entity} · {Institution} {Kind} ••{last4}"`, overridable per call with `naming` and per row
with `name`. It disambiguates entities, it is stable (a re-run yields `link`, never a `(2)`), and it
carries the last4 so a human can check a row against paper. It fits ezBookkeeping's 64-character
account name limit; a longer rendering is truncated in the middle of the institution, never the last4,
and the plan shows the truncation.

### 15.3 Kind to ezBookkeeping category — and why this is the decision to read aloud

ezBookkeeping has no on-budget/off-budget switch. Its equivalent consequential decision is the
**account category**, because it decides asset versus liability and therefore the sign of every
balance and the side of net worth it lands on (`pkg/models/account.go` asset/liability maps):

| `kind`      | Category                 | Side          | Why                                                         |
| ----------- | ------------------------ | ------------- | ----------------------------------------------------------- |
| `checking`  | `checking`               | asset         | money you spend                                             |
| `savings`   | `savings`                | asset         |                                                             |
| `cash`      | `cash`                   | asset         |                                                             |
| `card`      | `credit_card`            | **liability** | the balance owed is negative; payments are transfers in     |
| `brokerage` | `investment`             | asset         | market movement is not income — it stays out of income/expense by construction |
| `loan`      | `debt`                   | **liability** |                                                             |
| `cd`        | `certificate_of_deposit` | asset         |                                                             |

Controlled by `kind_to_category{}`, echoed, and explained per row. A credit card created as a checking
account turns every payment into "income" and inverts the card's balance — invisible for months, one
line to confirm.

**Currency is the second decision.** It is immutable after creation (§10.2), so the plan prints it for
every `create` row and flags any row whose currency was defaulted rather than stated in the manifest.

### 15.4 `POST /ingest/accounts/apply` (write)

Takes the token, creates the `create` rows through upstream's own account-create handler (one call per
account, journalled as one undoable batch), links the `link` rows, and **writes the map** beside the
statements, so the next `/ingest/plan` has a complete mapping and the operator never hand-writes a file of
27 account ids. `dry_run` defaults true.

**The opening balance (LOCKED).** A created account whose manifest row carries an opening balance is
created with `balance` = that amount and `balanceTime` = **11:59:59 UTC on `opening_date`**: upstream then
inserts the account's one Balance Modification transaction in the same database transaction.
ezBookkeeping refuses any transaction dated at or before an account's Balance Modification, and a
statement pipeline dates its rows at noon UTC, so the opening sorts strictly first while still showing on
its own date from UTC−11 to UTC+11. An account that is linked, not created, is never given an opening
balance — a Balance Modification can only be the first transaction an account ever has.
Code: `ingApplyAccounts()` and `ingOpeningTime()` in `~/BGit/Bryan_git/ezbookkeeping/pkg/machine/ingest_accounts.go`.
Spec: import_formats.mdx §9.3.

## 16. The passthrough — the upstream API behind the key

`/machine/v1/api/*` forwards to the upstream `/api/v1/*` handler of the same path, **as the bound
user**, behind the same five gates.

**Why it exists.** Completeness on day one. The typed routes of §10 take phases to build; the
passthrough makes every upstream capability reachable from `ezbk` from P1, so the operator is never
told "that needs a new route" for something the UI can already do.

**Why it is fenced (LOCKED).**

| Upstream path class                                                      | Tier       |
| ------------------------------------------------------------------------ | ---------- |
| any `GET`                                                                | read       |
| any `POST` not below                                                     | write      |
| `*/delete.json`, `*/batch_delete.json`, `data/clear/*`, `*/remove_unused.json` | **admin** |
| `tokens/*`, `users/2fa/*`, `users/external_auth/*`, `users/avatar/*`, `llm/*` | **refused** (404) |

- **No dry run, no confirm token, no ceiling, no journal.** The passthrough is the upstream API, not
  the machine plane's write protocol. That is exactly why **the MCP never calls it** (mcp.mdx §9.5) and
  why `ezbk` reaches it only through `ezbk raw`, which prints a one-line warning on every write.
- **The envelope is ours; `data` is upstream's `result` verbatim**, including upstream's big-integer
  strings — the passthrough is the one place R2's integer conversion does not apply, and
  `meta.passthrough: true` says so.
- **A typed route supersedes.** When §10 has a route for something, `ezbk` verbs use it, and the
  passthrough remains only as the escape hatch. A passthrough call that is made twice for the same
  purpose is a signal a typed route is missing.

This is the machine plane's answer to Actual's `/query` hatch: ezBookkeeping has no query language to
expose, and **raw SQL is never exposed** (§19.3), so the upstream API is the hatch.

## 17. Money, time and identifiers

### 17.1 Integer hundredths, everywhere (LOCKED — R2)

`-12350` with `currency: "USD"` is `-$123.50`. ezBookkeeping stores every amount as an int64 at a
**fixed scale of two decimal places for every currency** (`pkg/models/transaction.go`; `1234` is
12.34), including currencies that have no minor unit in real life — `1234` JPY in ezBookkeeping is
¥12.34. The plane keeps the app's scale exactly and never re-scales per currency: a yen amount of
¥5,000 is `500000` here, as it is in the database. Clients render with the currency's conventional
decimals; the wire never changes scale.

- **No floats.** Not once.
- **No decimal strings on the wire either** — which is a real change from upstream, whose account
  balances and statistics amounts are big-integer **strings** (`"123450"`) and whose MCP uses decimal
  strings (`"1234.50"`). The plane converts upstream's integer strings to JSON integers in exactly one
  place, `money.go`. It is lossless: upstream's per-amount range is ±999,999,999,999,999, inside
  JSON's safe integer range (2⁵³−1 ≈ 9.007 × 10¹⁵). A **sum** that exceeds the safe range is refused
  with `upstream_error` naming the field rather than rounded — a household will never see it, and a
  silent float is worse than a loud error.
- The clients call their own renderer for display; `--format json` and every MCP response carry the
  raw integer.
- A test round-trips adversarial values — `-1`, `0`, `1`, `99`, `-99`, `100000000`,
  `999999999999999` — through every layer, and a canary greps `pkg/machine/` for `float64` outside
  `money.go`'s rate handling.

**Exchange rates are the one non-integer.** A rate is a ratio, not money. It travels as upstream
supplies it (a decimal string) and is used for exactly one multiplication inside `money.go`, with the
result rounded once to integer hundredths.

### 17.2 Signs

Income positive, expense as a positive `amount` with `type: expense` in upstream's model — ezBookkeeping
stores the magnitude and the type carries direction. The plane's **analytics** and **balance** routes,
which are ours, use signed integers (negative is money out) so a series can be charted without
knowing each row's type; **transaction** routes keep upstream's `{type, amount}` shape verbatim. Each
route's entry says which convention it uses, and the two never mix inside one response.

### 17.3 Absent is not zero (LOCKED — R3)

ezBookkeeping has no budget, so Actual's `budgeted: null` case does not arise. The rule survives in
the places it applies here:

- A category with **no transactions** in a period is **absent** from a breakdown, not present with
  `0` — and `include_zero: true` lists it explicitly with `amount: 0` **and** `count: 0`, so a zero is
  always a counted zero.
- An average over a period with no data is `null`, not `0`.
- An account with no transactions has a real balance (its opening balance) and
  `firstTransaction: null`.
- A balance we could not compute is an error, not `0`.
- A converted total missing a currency's rate is `partial`, not a smaller number (§13.2).

### 17.4 Time

- **Dates on the wire are `YYYY-MM-DD`; months are `YYYY-MM`; instants are RFC 3339.** Upstream's API
  takes unix seconds plus a `utcOffset` in minutes; `clock.go` converts, in exactly one place.
- **Ranges are inclusive on both ends** and every response echoes the unix range it resolved.
- **The timezone decides what "a day" is.** Resolution: the call's `X-Timezone-Name` → the credentials
  file's `ezbookkeeping.timezone` → the server machine's local zone. Echoed in `meta.timezone`.
- **Each transaction keeps its own offset** (`TimezoneUtcOffset`) — the offset in force where it
  happened. Upstream's statistics accept `use_transaction_timezone`; the plane passes it through and
  echoes it, because "spent in March" for a transaction made in Tokyo at 08:00 on 1 April local time
  depends on which clock you ask.
- **No relative dates on the wire.** "Last month" is the client's to resolve, and the response says
  which month it decided.
- `transactionTime` in responses is **unix milliseconds** — upstream stores milliseconds so each
  user's times are unique (the extra digits are a sequence, not precision). The plane returns it
  verbatim and adds `date` (`YYYY-MM-DD` in the resolved zone) beside it.

### 17.5 Identifiers

ezBookkeeping ids are int64s from its own generator, serialised by upstream as **strings**
(`json:"id,string"`) because they exceed JavaScript's safe range. The plane keeps them as strings,
always. A client that parses an id into a number has already corrupted it; the CLI and the MCP treat
ids as opaque strings, and a test sends an id above 2⁵³ through every route.

Where a name is accepted instead, resolution is exact-match-first, then case-insensitive, and
**ambiguity is an error carrying the candidates**.

## 18. Concurrency, limits and performance

- **One process, one writer.** SQLite serialises writes; the plane additionally serialises its own
  writes at concurrency 1, so a second machine-plane write waits rather than racing a first. If it
  waits past its timeout it gets `conflict` with a retry hint, never a partial apply.
- **Reads are unbounded** and do not block on a write.
- **No cache on this plane.** Upstream's services read the database; a cache here would be a second
  copy that can be stale.
- **Long routes stream progress.** `/ingest/apply` and `/ingest/extract` accept
  `Accept: application/x-ndjson` and emit progress lines, ending with the normal envelope — so a client
  can draw a progress bar and never look hung. Upstream already tracks import progress
  (`GET /transactions/import/process.json`); the plane reports the same numbers. With plain
  `Accept: application/json` they take as long as they take, and **there is no server-side timeout on
  them**.

| Limit                    | Value       | Behaviour over it                        |
| ------------------------ | ----------- | ---------------------------------------- |
| `limit` on a list        | cap 5,000   | clamped, `truncated: true`               |
| Response bytes           | 16 MiB      | `truncated: true` + narrowing hint       |
| Request bytes            | 16 MiB      | `invalid_input`                          |
| `max_changes` on a write | default 200 | refused, **reporting the real count**    |
| Per-call timeout         | 30 s        | `upstream_error`; ingest routes exempt   |
| Tags per transaction     | 10          | upstream's; refused per row              |
| `/analytics/*` range     | 50 years    | `invalid_input`                          |

## 19. Security

### 19.1 Threat model

| #   | Threat                                                | Control                                                                                                        |
| --- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 1   | Another computer reaches port 8080                    | Gate 1, on `c.Request.RemoteAddr`, never `ClientIP()` / `X-Forwarded-For`                                       |
| 2   | A web page the operator has open calls the plane      | Gate 2 (origin + host) and gate 3 (the key it cannot read)                                                     |
| 3   | Another user on this machine                          | Gate 3; the key file is 0600 and ownership-checked                                                             |
| 4   | An agent writes something the operator did not want   | Gates 4 and 6: server tier, client switch, `dry_run` default, a token only a plan produces, a ceiling, undo    |
| 5   | A malicious transaction comment steers a model        | §19.4 — untrusted fields are marked, never executed                                                            |
| 6   | A secret leaks into a log, an error or a context      | §19.3 — fingerprints only; upstream's request log checked                                                      |
| 7   | A bad plan is applied against a changed ledger        | §9.3 — fingerprint recomputed at apply                                                                         |
| 8   | The operator's statement archive is damaged           | §14.2's conflict rule and §14.9's never-list                                                                   |
| 9   | The wrong user's books are read or written            | §6 — never guess a user; `meta.user` on every response                                                         |
| 10  | An upstream full-access token door left open          | §2.2 — `ezbk doctor` flags `enable_api_token` / `enable_mcp`                                                   |

### 19.2 No egress

The machine plane makes no outbound network call of its own. It does not call upstream's LLM
recognisers, does not fetch exchange rates on demand (it reads what upstream's own scheduled fetch
stored), and does not fetch map tiles. A test runs the full suite with outbound networking blocked.

### 19.3 What is never exposed

The API secret key (fingerprint only); `[security] secret_key`; any user's password hash, salt, 2FA
secret or recovery codes; any upstream JWT or `token_record.secret`; OAuth2 client secrets; LLM API
keys; mail passwords; absolute filesystem paths outside the statements root (the paths `/whoami` does
report — `installPath`, `credentialsFile`, `statementsRoot` — are rewritten under the home directory as
`~/…` by `homeRelative()` in `routes_plane.go`; a path outside the home directory passes through);
environment variables; SQL strings; stack traces (they go to `~/T/ezbookkeeping/error.err`, never into
a response). **Raw SQL is never accepted as input** — there is no query escape hatch that
takes SQL, and none is planned.

A **canary test** calls every route in `/capabilities` against a fixture database and greps every
response for the key pattern, for `secret`, `password`, `salt`, `token`, and `/Users/`.

### 19.4 Prompt-injection posture

A transaction comment, an account name, a category name, a tag and a statement description are
**operator-supplied data that may have been written by a third party** — a merchant chose that
descriptor, not the operator.

- Responses mark them: `meta.untrusted: ["comment", "name", "description"]`.
- The plane never interprets them as instructions, never uses them to choose a route, and never
  reflects them into a `hint`.
- [ai/mcp_prompt_ezbookkeeping.md](../ai/mcp_prompt_ezbookkeeping.md) carries the matching instruction
  on the model's side: text from the books is _evidence about money_, never a directive.

### 19.5 The audit trail

Every write appends one line to `~/T/_ezbookkeeping/machine.audit`:

```
2026-09-21T18:41:02Z  route=/ingest/apply  tier=write  caller=ezbookkeeping-mcp/0.1.0  user=operator  token=cf_01J8…  changed=117  ok=true  took_ms=8412
```

No amounts, no comments, no account names — **what happened, not what it was about.** `caller` comes
from `X-Ezbk-Client` and is advisory. The journal (§9.6) is the undo mechanism; the audit file is the
human-readable history, and it survives a database restore.

## 20. Open-source safety (LOCKED)

This fork is public at `github.com/BryanStarbuck/ezbookkeeping`. Three rules, each with a test:

1. **No secret in the tree.** No config key anywhere under `pkg/machine/`, `cli/`, `mcp/` or `conf/`
   can hold the API secret key. `data/.secret_key` is under `/data/`, which `.gitignore` already
   excludes, and it is not the API key anyway (§5.2). A test greps the built binaries and the tree for
   64-hex literals.
2. **No private path in the code.** The statements root, the bound username, entity names and account
   last-fours are **all configuration, none constants**. **Every entity, institution and account in
   this spec is invented** — `household`, `acme_llc`, `Northbank`, `Meridian`, `••4021`, `operator`.
   A test greps the source for `/Users/`, for the archive directory name and for the entity names used
   on this machine.
3. **No financial data in the repo.** `data/ezbookkeeping.db` lives under the git-ignored `/data/`;
   the statements tree and staging directory are outside the repo; fixtures are synthetic.

**The upstream-contribution line.** Anything here that belongs to every ezBookkeeping user — a
converter fix, a statistics bug — goes upstream to `mayswind/ezbookkeeping` as its own small PR, not
into `pkg/machine`. The machine plane is this fork's; the converters and services are everyone's.

## 23. Acceptance criteria

The plane is done when all of these hold:

1. On a machine with no `~/.credentials/ezbookkeeping.json`, `just run` mints a 64-hex key at `0600`
   with no operator action, and a second `just run` reuses it unchanged.
2. `GET /ping` answers with the key and 401s without it; from a non-loopback address it 404s even
   with the key — including when the server listens on `0.0.0.0`.
3. `GET /capabilities` lists every mounted route, and §11's coverage fixture matches it.
4. Every route in §10 exists, validates its input, and returns the envelope — including its errors.
5. **Every ✅ cell in §11 is exercised by a test** that performs the action and asserts the books
   changed the way the UI would have changed them.
6. Every write defaults to `dry_run: true`, refuses without a token, and reports the real count at the
   ceiling.
7. `/ingest/plan` and `/ingest/apply` report identical counts over an unchanged ledger; a second full
   import adds zero; a deleted imported row stays deleted.
8. `POST /undo` restores the user's rows to a byte-identical state after every write route.
9. No float, no decimal string and no big-int string appears in any typed-route response.
10. No typed route returns a total spanning two currencies without naming the rates.
11. The gate ladder's negative suite passes, including `X-Forwarded-For` and `Origin`.
12. The leak canary passes across every route and the server log.
13. The three open-source canaries pass.
14. Upstream's `go test ./...` still passes, and `cmd/webserver.go` differs from upstream by the mount
    line only.
15. `just build && just run && ezbk doctor` is green on a machine that has never run this, with no
    manual key step.

## 25. Invariants recap (LOCKED)

1. Loopback only, forever — on the real socket peer, whatever the listener is bound to.
2. The API secret key is 256 bits from `crypto/rand`, 64 hex, in `~/.credentials/ezbookkeeping.json`
   at 0600, minted by the web app on first boot and reused thereafter, never in the repo.
3. It is compared in constant time and never logged except as a fingerprint.
4. It is not an upstream token, not `[security] secret_key`, and never accepted by `/api/v1` or `/mcp`.
5. The plane binds to exactly one user and never guesses between several.
6. Five gates before any handler, six before any write. Fail closed at every one.
7. One envelope. Nine error codes. Every error names a fix.
8. Money is integer hundredths, everywhere, always — at the app's fixed scale for every currency.
9. Every amount carries its currency; no total crosses currencies without named rates.
10. Absence is reported as absence, never as zero.
11. Every write has a dry run built from the write's own first half; a write needs two switches, a
    `dry_run: false` and a token only a plan could produce.
12. The machine plane is the duplicate authority for imports, with one implementation and a durable
    record; a deletion is never undone by an import.
13. One service call per route; composed routes say so and are named in this spec.
14. Nothing is computed twice. If a client would have to sum or convert it, it becomes a route here.
15. Every cap is reported.
16. Deleting is admin-tier, and the MCP does not have it; undo deletes only what undo's journal created.
17. The delta to upstream's files is one mount line and one arm call.
18. No secret, no private path and no financial data in this repo.
